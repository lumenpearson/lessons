# ELSCHOOL — АИС «Образование» Республики Башкортостан

*Part of [the electronic diaries of Russia’s regions](../diaries.md). Verification: extracted, checked against the code, and dated. Confidence of the whole: medium. Nothing here has been tried against the live service.*

**The outgoing diary of Башкортостан.** The republic moves to the МЭШ-based
[«Моя школа»](mesh-myschool.md) at `dnevnik.edurb.ru` in the 2026/27 school year — most schools
from 1 September 2026, the rest by the end of the year — so everything on this page is a system
on its way out. `edu.brsc.ru` is its older address and redirects here.

**Two surfaces.** Nine independent clients from 2021 to November 2025 scrape the ASP.NET site
at `elschool.ru`: a form login at `/Logon/Index` sets a `JWToken` cookie, and the diary, the
grades and the results are HTML pages. A JSON API at `api.elschool.ru/api/<method>` also exists,
but it rests on one source, a 2022 package whose repository is gone, and most of its rows are
marked uncertain for that reason.

**What is missing.** Every client signs in as a pupil. How a parent with two children picks
one, and how the Госуслуги sign-in the site offers hands back its cookie, no client shows.

**Signing in.**

*Web form login (JWToken cookie) — used by every scraper* — token carried as cookie: JWToken. Lifetime: Sample JWT (Kiera38/elschooltgbot tests/test_register.py, January 2023): nbf 1674068400, exp 1674673200 → 7 days. Ilya-Repin/elschool-api caches it for 172800 s (2 days) and its schema comment says the lifetime «must be less than a week».. Refresh: None. Clients re-POST /Logon/Index with the stored login and password when the token check fails; Kiera38's bots also let the user paste a JWToken by hand..

1. POST https://elschool.ru/Logon/Index (same URL as the form page; form action="") with application/x-www-form-urlencoded body `login=<login>&password=<password>&GoogleAuthCode=` (Ilya-Repin/elschool-api and Ilya-Repin/Elschooler send the empty GoogleAuthCode field; Ramin2009Mc, archievega, code-1080 and Armagagedone send only login+password as form data; Kiera38 sends login and password as QUERY parameters of the POST and it works; paochapro sends a multipart/form-data body; theslothbear/renatpro first GETs the form, then POSTs login, password and `_xsrf` (set to None), with a Chrome User-Agent and Referer). No captcha, no CSRF token was required by any client, and the archived form carries none.
2. Do not follow redirects. Success is HTTP 302 whose body/Location points to /users/privateoffice; the response carries `Set-Cookie: JWToken=<JWT>`. Wrong credentials also answer 302 (back to the logon page) with no JWToken cookie — Ilya-Repin checks that the 302 body contains the string "privateoffice"; Kiera38 follows redirects and checks that the final URL starts with https://elschool.ru/users/privateoffice, paochapro that it equals it.
3. Read the JWToken cookie. It is an HS256 JWT signed by the server; clients decode it WITHOUT verification to get the ids needed for every diary URL: claim `Id` = pupilId; claim `role` = comma-separated "<RoleId>,<EntityType>,<empty>,<rooId>,<instituteId>,<departmentId>," (sample: "8,Department,,54,1207,210594," → role 8, rooId 54, instituteId 1207, departmentId 210594). Other claims: MustChangePassword, ESIALogon ("False" for a password login), AvailableRoles, nbf, exp, iat, iss (an internal IP), aud "it.brsc.ru".
4. Alternative to decoding: GET https://elschool.ru/users/diaries with the cookie and do not follow the 302; the body is "Object moved to <a href="/users/diaries/details?rooId=..&amp;instituteId=..&amp;departmentId=..&amp;pupilId=..">here</a>" — Ilya-Repin cuts the substring between "?" and "here" and strips "amp;" to get the query string. Or fetch the page (following redirects) and take the href of the «Табель» link (Kiera38) / the a.dropdown-item[model-department-id] entries to pick another class year (Armagagedone, paochapro).
5. Send the cookie `JWToken=<JWT>` on every subsequent GET to elschool.ru. Validity check used by Ilya-Repin: GET /privateoffice with the cookie — the C++ elschool-api does it with follow_redirects(false) (200 = valid, anything else = expired); the Go Elschooler's CheckToken uses a default http.Client that follows redirects, so its 200 test cannot actually detect expiry. No client uses /users/privateoffice as the probe.
6. Logout: POST https://elschool.ru/users/diaries/Exit (Armagagedone) — only one client does it; the others simply drop the cookie.

   The form has a GoogleAuthCode field (TOTP second factor) that every client leaves empty; the JWT's ESIALogon claim and the site's Госуслуги integration imply an ЕСИА login path, but no open-source client implements it. Kiera38 disables TLS verification (ssl=False) for elschool.ru; renatpro sets verify_ssl=False too — a certificate-chain problem on the host at the time, not an API requirement. The real form (Wayback 2022-01-23) has a #twofa-check checkbox that reveals the GoogleAuthCode input; the site's script no longer requires it to be filled. Still the flow of the newest clients (Ramin2009Mc 2025-11-29, renatpro 2025-09-01).

*api.elschool.ru token (aioelschools, 2022)* — token carried as query: token. Lifetime: unknown — not stated anywhere in the package. Refresh: none — call login.token.get again.

1. GET https://api.elschool.ru/api/login.token.get?login=<login>&password=<password>
2. Parse the JSON body with content_type text/plain; on `status == "ok"` take `result.Token` (the `result` object also carries Id, Login, Password, Email, INN, SNILS, BornDate, Photo, FirstName, LastName, MiddleName and Roles[{Id, RoleId, UserId, RoleName, EntityType, EntityName, ChildId}]).
3. Pass `token=<Token>` as a query parameter on every other method, together with `userid` (the user's Id) or `departmentid`/`childid` as the method requires. `login.users.get?token=` lists the users (children) reachable with the token.
4. Any non-200 or `status != "ok"` answer carries `error: {code, description}`; the client raises APIError[code]. `user.twofactorcheck.get?userid&token` returns a boolean — whether the account has a second factor.
5. dictionary.* methods take no token at all.

   The only evidence for this API is one 2022 PyPI package (aioelschools 1.0.0–1.0.6, all released 26–28 May 2022) whose GitHub repository is now a 404; its model docstrings say «не нашел информации» for several results. Whether api.elschool.ru still answers these methods in 2026 is unverified.

*ЕСИА / Госуслуги sign-in (web, not implemented by any client)* — token carried as cookie: JWToken (presumed). Lifetime: unknown. Refresh: none known.

1. GET https://elschool.ru/logon/esia?type=login (link on the login page)
2. 302 to https://esia.gosuslugi.ru/aas/oauth2/ac with client_id=BRSC-GOSUSLUGI_ID-GATEWAY, redirect_uri=https://esia.brsc.ru/code/, scope=fullname, response_type=code, access_type=online, state=<uuid>, timestamp and a signed client_secret (Wayback capture of edu.brsc.ru/logon/esia?type=login, 2018-06-24)
3. After the ЕСИА consent the BRSC gateway esia.brsc.ru/code/ receives the code; when one ЕСИА identity maps to several elschool accounts the site shows an «EsiaChoose» page (#esia-choose-form with radio .check-esia-user) — the login script handles it. The end state is presumably the same JWToken cookie with claim ESIALogon=True; not observed.

   Evidence is archived pages only (2018 redirect, 2021 login script); no open-source client drives this flow, and the ЕСИА leg needs a real browser.

**Headers the clients send.**

| Header | Value | Why |
| --- | --- | --- |
| `Cookie` | JWToken=<jwt> | The only credential for every elschool.ru page after login. |
| `Content-Type` | application/x-www-form-urlencoded | Login body format; set explicitly only by the Go Elschooler (the Python clients get it implicitly from a dict body, the C++ client sets only Content-Length; multipart also accepted — paochapro). |
| `User-Agent` | Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/75.0.3770.142 Safari/537.36 | Set by theslothbear/renatpro together with Referer: https://elschool.ru/Logon/Index; the other eight clients use their library defaults (python-requests, aiohttp, okhttp, curl) and report no blocking, so it is not required. |

No X-* subsystem headers, no device tokens, no SMS. The GET /users/diaries → 302 → /users/diaries/details?rooId&instituteId&departmentId&pupilId redirect is the canonical way to learn the four ids without decoding the JWT. Password recovery is a three-step ajax flow: POST /logon/recovery {Login} → GET /logon/recoverycode?login= → POST /Logon/RecoveryCodeAjax {login, code} → GET /Logon/RecoverPassword?Login=&Code=. Currency (2026-09-24): the newest public clients (Ramin2009Mc 2025-11-29, renatpro 2025-09-01) still use the plain form login with no captcha and no ЕСИА requirement; nothing newer exists on GitHub, and elschool.ru answered 503 to WebFetch, so a 2026 change to the form cannot be ruled out. The successor dnevnik.edurb.ru (МЭШ) is ЕСИА-only, but that belongs to the fgis_myschool/МЭШ platform.

**Formats.**

- *Dates*: HTML: dd.mm.yyyy everywhere («Дата урока: 01.03.2023<p>Дата проставления: 26.04.2023» in mark popovers; td.diary__dayweek shows «Понедельник dd.mm» without a year); lesson times as HH:MM-HH:MM. Week selection: calendar year + ISO week number (Python date.isocalendar()[1], Java Calendar.WEEK_OF_YEAR) as Year/Week (case-insensitive) on /users/diaries/details. api.elschool.ru: year + week integers on user.diary.get; startdate/enddate strings of unspecified format on chart.* ; response date fields are strings (StartDate, EndDate, CreatedDate, CalendarDate, MarkCreateDate).
- *Ids*: All integers. rooId = district education authority (РОО), instituteId = school, departmentId = class (changes every school year; one pupil has several), pupilId = student = JWT claim Id = api userid. The JWT role claim packs them as "<roleId>,<EntityType>,,<rooId>,<instituteId>,<departmentId>,". api.elschool.ru uses lower-case query names (userid, departmentid, instituteid, childid, systemperiodid) and PascalCase JSON fields (Id, UserId, DepartmentId, LessonId ...).
- *Pagination*: None. The diary is fetched one week at a time via Year/Week; the report card and final marks return the whole year in one page; api.elschool.ru methods return whole lists in `result`.
- *Notes*: api.elschool.ru envelope: {status: 'ok' \| other, error: {code: string, description: string}, result: ...} with HTTP 200 and Content-Type text/plain; charset=utf-8. Web pages are UTF-8 HTML with &nbsp; padding in day headers and averages written with a decimal comma («4,52»). Period names are «1 четверть»…«4 четверть» or «1 полугодие»/«2 полугодие», read from the table headers.

**Caveats.**

- Everything is reverse-engineered; there is no official API documentation. The web routes (Logon/Index, users/privateoffice, users/diaries, users/diaries/details\|grades\|results) are corroborated by nine independent clients from 2021 to November 2025 and the markup has stayed stable, so they are the reliable part.
- The api.elschool.ru JSON API rests on a single source: the aioelschools PyPI package (seven releases in three days in May 2022, pydantic<=1.9, aiohttp<=3.8.1), whose GitHub repository is gone and whose models carry «не нашел информации» docstrings for skud/billreplenishment/foodtransaction/markexam results. No other public code references that host and it answered 503 to a fetch during this research (as did elschool.ru itself, so the 503 is the fetcher being refused, not evidence that the host is dead), so every api.elschool.ru row is marked uncertain. Date formats for its startdate/enddate parameters are not shown anywhere.
- Only the student (role 8, «Department») view is covered. Parent accounts (several children — the api's login.users.get and childid hint at them), teacher and administrator surfaces are absent from every client.
- Every client uses the JWToken for the pupil that logged in; the only way seen to reach another class year is the model-department-id dropdown on the grades page. Nothing shows how a parent selects a child on the web site.
- The ЕСИА/Госуслуги login path exists (JWT claim ESIALogon, entry-wrapper button on the login page, vendor pages) but no client implements it; the GoogleAuthCode field of the login form is always sent empty, so the second-factor behaviour is unknown.
- The recovery and ЕСИА routes (/logon/recovery, /Logon/RecoveryCodeAjax, /logon/recoverycode, /Logon/RecoverPassword, /logon/esia, IndexInfo) come from Wayback captures of the site's own login script and pages (2018–2022), not from client code; api.elschool.ru/widgets/food/{guid} and the IndexInfo query parameters come from a search-engine listing only.
- edu.brsc.ru is the old entry host of the same АИС «Образование»; Wayback captures from June 2023 show it 301-redirecting every path to elschool.ru, and no client code references it. By mos.ru, Республика Башкортостан joins МЭШ «Моя школа» from the first quarter of 2026/27, and the МЭШ help table names dnevnik.edurb.ru as the region's entry — so every route here describes the outgoing system. How long elschool.ru keeps serving in parallel (archive of marks, canteen payments) is not stated in any source reached; «current» on a route means current for this platform, not that the region still relies on it after September 2026.
- The token lifetime (7 days) is derived from one sample JWT from January 2023; the C++ client's 2-day cache and «must be less than a week» comment are the only other evidence.
- Kiera38's bots and renatpro disable TLS verification against elschool.ru; the reason (certificate chain) is not stated and may no longer apply.
- The Wayback Machine holds no capture at all of api.elschool.ru or file.elschool.ru, so nothing independent of aioelschools corroborates the JSON API.
- No newer public client than November 2025 exists, and neither the vendor's pages nor web.archive.org could be read in the currency pass (503 / unreachable), so any 2026 change to the login form (captcha, ЕСИА-only) would not be visible here.
- The two edu.brsc.ru /User/Diary* rows are legacy and rest only on Wayback CDX URLs captured as 302s in 2017; their response format is unknown.
