# МЭШ — «Московская электронная школа», Москва

*Part of [the electronic diaries of Russia’s regions](../diaries.md). Verification: extracted, checked against the code, and dated. Confidence of the whole: medium. Nothing here has been tried against the live service.*

**The largest surface of any diary in the country, and the best-studied one.** 431 routes, most
of them current, on `school.mos.ru`; the older `dnevnik.mos.ru` families — `core/api`,
`jersey/api`, `mobile/api`, `reports/api` — are still answered but are marked legacy, because
the official app has moved off them. The same code base, deployed for other regions, is
[«Моя школа»](mesh-myschool.md), and the Perm diary [ЭПОС.Школа](epos.md) is an older fork of
it; a client written for one of the three reads most of the other two.

**Signing in is the hard part, and it is getting harder.** The official app registers itself
with `login.mos.ru` — the city's own identity provider, where Госуслуги is only one button — and
runs an OAuth2 flow with PKCE in a browser. Third-party clients that post the password
headlessly still exist, but `login.mos.ru` now asks a headless caller for a hashcash
proof-of-work and fingerprints it, so that route drifts fastest and the pre-2024 form login no
longer works unmodified. Once signed in, the diary token travels as `Authorization: Bearer`,
often duplicated as `Auth-Token`, with `Profile-Id` naming the pupil.

**Where to start reading.** The Mag329 fork of OctoDiary-py (February 2026) and OctoDiary-kt
(May 2026) are the maintained clients; a decompiled string table of the official app is what
dated most rows. Rows marked *uncertain* come only from that string table or from a single
write-up.

**Signing in.**

*Official app: register -> browser authorization (mos.ru password, SMS code or «Войти через Госуслуги») -> mos.ru token -> МЭШ token (ru.mes.dnevnik, bundle 2026-08)* — token carried as header Authorization: Bearer <mesh token> (hand-written apiRequest also sends Auth-Token: <token> and Profile-Id); the mos.ru token only as Authorization on login.mos.ru. Lifetime: JWT exp; the app runs a token-expiration timer for the mos.ru token.. Refresh: МЭШ token: POST https://school.mos.ru/v3/token/refresh form refresh_token=<mesh_refresh_token> -> 201 {access_token, refresh_token}. mos.ru token: POST /sps/oauth/te grant_type=client_credentials&scope=<scopes> (refreshSudirToken, headless) or refresh_token. Transport token for pay.mos.ru: te grant_type=urn:ietf:params:oauth:grant-type:token-exchange, token_format=opaque..

1. POST https://login.mos.ru/sps/oauth/register with Authorization: Bearer <initialAccessToken shipped in the app, redacted> and JSON {software_id: "dnevnik.mos.ru", device_type, software_statement: <signed JWT, redacted; iat 2024-12-20>} -> client_id, client_secret, registration_access_token, registration_client_uri.
2. Open in a browser GET https://login.mos.ru/sps/oauth/ae?scope=<openid profile birthday contacts snils blitz_change_password blitz_user_rights blitz_qr_auth …>&access_type=offline&response_type=code&state=<uuid>&client_id=<client_id>&redirect_uri=dnevnik-mes://oauth2redirect&prompt=login&code_challenge=<S256>&code_challenge_method=S256 (+ bip_action_hint=used_sms for the one-time SMS code). The page offers the mos.ru password, SMS code and «Войти через Госуслуги».
3. Catch dnevnik-mes://oauth2redirect?code=…; POST https://login.mos.ru/sps/oauth/te (Authorization: Basic client_id:client_secret, form grant_type=authorization_code&code&redirect_uri&code_verifier) -> mos.ru access_token/refresh_token.
4. POST https://school.mos.ru/v3/auth/sudir/auth {"user_authentication_for_mobile_request":{"mos_access_token":…}} -> user_authentication_for_mobile_response {mesh_access_token, mesh_refresh_token}; 422 accountDoesNotExist when the mos.ru account has no МЭШ account; the JWT must carry a role.
5. GET https://school.mos.ru/api/ej/acl/v1/mod-acl/users/profile_info (Auth-Token + Authorization: Bearer + Partner-Source-Id: MOBILE + x-mes-subsystem: familymp) -> [{id,type}]; with several profiles GET /v2/token/refresh?subsystem=2&roleId=<1 student\|2 parent> per profile (201, text JWT).
6. Call school.mos.ru APIs with Authorization: Bearer <token> (+ Auth-Token on the hand-written layer), X-Mes-Subsystem: familymp, client-type: diary-mobile, Accept-Language: ru, Profile-id.

   This is the current first-party flow. The app also confirms web sign-ins by QR (GET/POST https://login.mos.ru/sps/api/v3/auth/qr/{code}[/confirm\|/refuse]) and logs out via https://login.mos.ru/sps/login/logout?post_logout_redirect_uri=https://dnevnik.mos.ru or /logout/esia. It has no /sps/login/methods/headless path and no proofOfWork: the headless flow below is a third-party reproduction.

*Third-party headless mos.ru password (OctoDiary-py, Mag329 fork 2026-02, Learnify-bot 2026-04; not what the official app does)* — token carried as After sign-in the diary token is sent as header 'Authorization: Bearer <token>' and duplicated as header 'Auth-Token: <token>'; some clients also set Cookie aupd_token/aupdtoken=<token>.. Lifetime: mos.ru access token short-lived (JWT exp); mesh token refreshed via school.mos.ru /v2/token/refresh (per role) or /v3/token/refresh (refresh_token grant).. Refresh: GET https://school.mos.ru/v2/token/refresh?roleId=1&subsystem=2 (Bearer or aupd_token cookie) returns a new token as text; or POST /v3/token/refresh {refresh_token}; or POST /sps/oauth/te grant_type=refresh_token for the mos.ru side..

1. POST https://login.mos.ru/sps/oauth/register with the app's static Bearer issuer secret and software_statement -> per-install client_id/client_secret.
2. Generate PKCE code_verifier/code_challenge (S256).
3. GET https://login.mos.ru/sps/oauth/ae?display=script&client_id=...&code_challenge=... -> JSON with a proofOfWork challenge.
4. Solve the hashcash proofOfWork; POST /sps/login/methods/headless/password {login,password,proofOfWork} (keep session cookies).
5. If required: POST /sps/login/methods/headless/sms/bind (empty) then again with {sms-code}.
6. On success get trust_code (the OAuth code); POST /sps/oauth/te (Basic client_id:client_secret, grant_type=authorization_code, code, code_verifier) -> mos.ru access_token + refresh_token.
7. POST https://school.mos.ru/v3/auth/sudir/auth {user_authentication_for_mobile_request:{mos_access_token}} -> mesh_access_token (the diary token).

   OctoDiary-py/kt implement this fully. The static issuer Bearer and software_statement are embedded app credentials (redacted here). Reproduces with the app's registration identity what the official app does in a browser; depends on login.mos.ru keeping the headless JSON endpoints and the proofOfWork scheme, which no first-party code shows.

*QR-code login (scan from official app)* — token carried as Cookie aupd_token / header Authorization: Bearer <aupd_token>.. Lifetime: aupd_token JWT with exp; aupd_refresh_token for /v3/token/refresh.. Refresh: school.mos.ru /v2/token/refresh or /v3/token/refresh..

1. GET https://school.mos.ru/v3/auth/sudir/login -> HTML meta-refresh to login.mos.ru/sps/oauth/ae; follow it (MOSDiary). Learnify-bot instead calls GET /sps/oauth/ae?display=script&client_id=dnevnik.mos.ru&redirect_uri=https://school.mos.ru/v3/auth/sudir/callback directly and takes items[inquire=show_qr_code].link.
2. Poll GET https://login.mos.ru/sps/login/methods/headless/qrCode/pull (or /sps/login/methods/qrCode/pull?_=<ms>) -> command showQRCode with a link; render as QR.
3. User scans/confirms in the official Дневник МЭШ or mos.ru app; poll until command=needComplete.
4. POST /sps/login/methods/qrCode/complete (or /headless/qrCode/complete).
5. If a second factor is demanded: GET /sps/login/methods2/{sms\|email\|flashCall}?bo=..., for flashCall POST /sps/login/method/flashCall then POST /sps/login/method/flashCall/code {code}, else POST /sps/login/methods/{sms\|email}?bo= {<method>-code}; then POST /sps/login/ur/askToTrust {action}.
6. Collect aupd_token and aupd_refresh_token from the redirect cookies.

   MOSDiary and Learnify-bot implement this end to end.

*Browser / WebView cookie capture (manual token)* — token carried as aupd_token cookie -> reused as Authorization: Bearer / Auth-Token.. Lifetime: JWT exp (~ hours).. Refresh: Re-run /v2/token/refresh with the cookie..

1. Open a WebView/browser at login.mos.ru/sps/oauth/ae (or school.mos.ru/?backUrl=.../v2/token/refresh).
2. User signs in with mos.ru; the diary sets the aupd_token cookie on school.mos.ru / mos.ru.
3. Read the aupd_token cookie (or the text body of /v2/token/refresh) and use it as the bearer token.

   mesh_expressive (Android WebView), eger-ux and many bots just ask the user to paste the token from this URL. mos-diary-mcp uses Playwright with a real Chrome fingerprint to pass the KFP anti-fraud check.

*ESIA / Госуслуги via school.mos.ru /v3/auth/esia/login (OctoDiary-kt, browser)* — token carried as Authorization: Bearer <token>.. Lifetime: JWT exp.. Refresh: /v2/token/refresh..

2. GET https://school.mos.ru/v3/auth/token?code=...&state=... -> diary token.
3. Госуслуги captcha/MFA pages are completed by the person in the browser.

**Captcha and second factor.** In the first-party browser flow, SMS codes, second factors and any anti-bot checks are login.mos.ru pages completed by the person (bip_action_hint=used_sms selects the SMS code). login.mos.ru enforces a hashcash proofOfWork on headless password login and can demand SMS/e-mail/flash-call/TOTP second factors (/sps/login/methods2). The «Моя Школа» ESIA path adds a gosuslugi captcha (esia.gosuslugi.ru/captcha/api/public/v2). login.mos.ru also runs a browser-fingerprint anti-fraud (KFP) that blocks non-browser clients, which is why several clients use Puppeteer/Playwright with a real Chrome.

As of the official app bundle of 2026-08 the only first-party sign-in is the browser OAuth2 PKCE flow on login.mos.ru (password, SMS one-time code or Госуслуги on the same page) followed by /v3/auth/sudir/auth; nothing points to an ЕСИА-only switch for Moscow. Two token families exist: the diary token (mesh_access_token / aupd_token, a JWT carrying person guid, profile id and roles) used on all data endpoints, and the mos.ru OAuth access/refresh tokens used only against login.mos.ru. The diary token is carried both as Authorization: Bearer and as Auth-Token; refresh is role-scoped (roleId 1=student, 2=parent).

**Formats.**

- *Dates*: Query dates are ISO YYYY-MM-DD on the current family/web and family/mobile and eventcalendar APIs (from/to, begin_date/end_date, date, dates=comma-separated). The legacy dnevnik.mos.ru core/api uses DD.MM.YYYY (created_at_from, begin_prepared_date). Datetimes are ISO-8601 with Z. Timezone is Europe/Moscow.
- *Ids*: Numeric ids for profile/student (student_id, profile_id, class_unit_id, school_id, mark_id, lesson/schedule_item id, homework_entry_id). person_id / person_ids / contingent_guid are GUID strings (the 'person' identity), distinct from the numeric profile id. academic_year_id is numeric.
- *Pagination*: page/per_page (or size) on list endpoints (student_profiles, notifications, class members per_page up to 1000/Int.MAX_VALUE); search endpoints (contests, gamification, materials) take a page/pagination object with number+size in the JSON body.
- *Notes*: Most read endpoints wrap the list in a top-level 'payload' (family/web) or 'response' (eventcalendar) key. Marks values are strings ('2'..'5','н/а') with a numeric weight and control_form_name.

**Caveats.**

- No public API documentation exists: the routes are reverse-engineered from unofficial clients and one decompilation report; endpoints can change without notice and several are version-bumped (meals v1->v2->v3, day_balance_info->day-balance-info/v2, token refresh v2->v3).
- school.mos.ru is the current host; dnevnik.mos.ru core/api, jersey/api, mobile/api and reports/api are the older ЭЖД surface — marked legacy. Many endpoints answer on both hosts; the base_url in each row is the one the cited client uses.
- The 'uncertain' rows come only from the official-app string dump (AmetistYT/mesh_expressive decompiled/dnevnik_strings.txt), a single Markdown write-up (elix-start/MES), a link the client builds but never requests, or a client whose request is broken as written (RedGuyRu DELETE attendance); path shapes are trustworthy, query/body shapes are not.
- The official app 'Дневник МЭШ' (ru.mes.dnevnik) is React Native/Hermes and exposes ~hundreds more microservice endpoints (portfolio/*, api/claims, api/certificates, api/instantmessages, api/fcm, api/knowledge_skill, api/proforientation, api/aupd/*, etc.) visible as Redux action names in the string dump; only those actually called by open-source clients (or with a concrete path in the dump) are tabled, so the list is not exhaustive of the platform.
- login.mos.ru anti-fraud (KFP, proofOfWork, fingerprinting) and rotating anti-CSRF tokens mean the sign-in flows drift fastest; the legacy HTML-form flow (IvanProgramming, RedGuyRu Puppeteer) no longer works unmodified.
- Embedded app credentials (the static /sps/oauth/register issuer Bearer, the software_statement JWT, the uchebnik guest token, OctoDiary's verify-token) are present verbatim in the clients but are redacted here.
- Several clients are unmaintained: IvanProgramming/dnevnik_mos_ru (2024), RedGuyRu/node-redguy-dnevnik-api (2023, and it targets a third-party proxy dapi.redguy.ru rather than mos.ru directly), pixwet/SchoolMosregRuAPI (archived, targets the mosreg 'Школьный портал' not МЭШ).
- OctoDiary is dual-system: the same code base speaks МЭШ (mes: school.mos.ru/dnevnik.mos.ru/login.mos.ru) and «Моя Школа» (myschool: myschool.mosreg.ru/authedu.mosreg.ru/api.myschool.mosreg.ru/esia.gosuslugi.ru). Rows here use the МЭШ hosts; the myschool equivalents swap the host per OctoDiary's BaseURL table.
- Several rows exist on both hosts and clients disagree about which one: OctoDiary-py sends /api/ej/rating/v1/*, /api/persondata/mobile/*, /api/meals/v1/clients, /v2/token/refresh (myschool), web eventcalendar and core/acl calls to dnevnik.mos.ru, while OctoDiary-kt, mesh_expressive, libremesh and febdaynik send the rating calls to school.mos.ru. The base_url in each row is the cited client's.
- The official app string dump also carries ~100 "METHOD /path" strings relative to microservice prefixes it does not show (e.g. POST /attendance/v2, PUT /attendance, GET /children/{personId}/locations, /portfolio/entitites, /news/users, /stories/favorite/list, /devices, /banners/v2); without the prefix they cannot be placed on a host, so only the entries that carry a full /api/... or /portfolio/app/... path are tabled (as uncertain).
- Currency rests on code, not traffic: the official app bundle (decompiled Hermes, 2026-08; host selectors, auth sagas, generated OpenAPI clients and the vendor specs embedded for mocking) and OctoDiary-kt's git history (2025-02 to 2025-10 moves away from dnevnik.mos.ru). No host could be probed from this session and web search was exhausted, so no 2025–2026 announcement about МЭШ sign-in was read; the official help page fetched covers only the regional nodes (Госуслуги-only there).
- Routes added from the official app's generated clients exist as code in a shipping app, but a generated client contains every operation of its spec whether or not a screen calls it; they are «current» in that sense only. Request/response schemas are in the embedded vendor specs, not reproduced here.
- Moscow is not among the regions moving to ТОР «Моя школа» / «Госуслуги Моя школа» as far as the sources show; the МЭШ-based regional nodes and their migration dates belong to mesh_myschool and fgis_myschool.
- dnevnik.mos.ru rows are kept with the status their newest caller justifies: current where a client maintained in 2026 still sends them (/acl/api/users/profile_info), legacy where a maintained client moved away, uncertain where only OctoDiary-py (2024) sends them.
- Rows whose source file is decompiled/dnevnik_decompiled.js come from the official app's OpenAPI-generated clients; «spec «…»» in the symbol names the embedded vendor spec that documents the schema. Their headers are the app's common interceptor set.
