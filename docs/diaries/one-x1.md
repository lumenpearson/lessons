# The «one.» platform — Кировская, Псковская, Запорожская, Оренбургская and more

*Part of [the electronic diaries of Russia’s regions](../diaries.md). Verification: extracted, checked against the code, and dated. Confidence of the whole: medium. Nothing here has been tried against the live service.*

**One code base under different regional names, with no name of its own in any source.** Each
region runs a portal at `one.<region-domain>` behind a sign-in at `passport.<region-domain>`.
Four regions are confirmed by client code or an official manual: Кировская область
(`one.43edu.ru`, since 2022, replacing «Аверс»), Псковская (`one.pskovedu.ru`), Запорожская
(`one.umnik-zo.ru`) and Оренбургская (`de.edu.orb.ru`, signed in through `edu.orb.ru`). Three
more carry the same pair of hosts and the same login page, but no client has been seen there, so
they are *likely* rather than known: Ставропольский край (`one.stavminobr.ru`, since January
2025), Чукотский АО (`one.edu87.ru`) and Орловская область (`one.obr57.ru`, found by the region
survey). Астраханская's `one.astrobl.ru` looked like one of them and is not: it runs ЭлЖур.
Inside, it is a PHP application on Yii with a Sencha Ext.Direct front end; the wire names — the
`X1_SSO` cookie, the `X1API` action, the `SYS_GUID` of every record — are why this page calls
it «X1» where it needs a word.

**Signing in.** `passport.` takes a login and a password, or a СНИЛС and a password, and sets
`X1_SSO`; Госуслуги is the alternative on every region, and the newest client also signs in by
a QR code the Госуслуги app scans. The Оренбургская bot gets by with a plain `PHPSESSID` on
`de.edu.orb.ru`, the Псковская client says that is not enough there, so which cookie a region
wants has to be checked per region. The diary itself is plain REST — `/edv/index/diary/{GUID}`
for a week, `/edv/index/report/*` for marks — proven identical on the Кировская, Псковская and
Оренбургская servers and assumed elsewhere.

**A mobile API beside the portal.** Орловская's app talks to `mp2.obr57.ru`, not to the portal:
after the Госуслуги sign-in yields `X1_SSO`, it posts JSON to `/journals/login` and
`/session/initsession` and then to `/journals/diaryday`, `/journals/allperiods`,
`/journals/marksbyperiod` and `/journals/periodmarks`. It sends no cookie and no bearer token: the
session travels in the body, as the raw `X1_SSO` beside an encrypted per-session key, with the
app's `X-Requested-With` header. All seven rows were read verbatim from one client of 2026,
`vodolazny/burmalda57`; no other region's `mp2.` host has been seen, so whether they run the same
mobile API is unknown.

**What is thin.** Of the portal's fifty-four rows thirteen are current and the rest uncertain, because
the richest client, `pskovedu-sdk`, was written in one day, calls itself «vibe-coded» and marks
its own Ext.Direct, ORM and ЕСИА calls unverified. From September 2026 families in these regions
are pointed at «Госуслуги Моя школа», and Оренбургская's ministry calls September a phased
transition to it, though the region is not on the official list of the twenty that switched and
`de.edu.orb.ru` still runs; the portals stay the regions' journals behind the app, so a client of
`/edv` may keep its server and lose its users.

**Signing in.**

*passport login/password (Кировская; same pattern all regions)* — token carried as cookie X1_SSO. Lifetime: session cookie; re-login when diary JSON success=false.

1. POST https://passport.43edu.ru/auth/login with form login (email or СНИЛС), password, submit=submit, returnTo=https://one.43edu.ru
2. server sets X1_SSO cookie on *.43edu.ru
3. GET https://one.43edu.ru/ once, then reuse cookie on /edv and /report

   Two.Diary (app/parse.py auth, app/diary_class.py). Branded entry points one.<region>.ru/auth/login + passport.<region>.ru documented for Pskov, Kirov, Orenburg (de.edu.orb.ru), Stavropol, Zaporozhye, Chukotka. STATUS 2025-26: regional instructions for Kirov, Pskov, Stavropol and Orenburg describe ESIA («Вход через портал госуслуг», confirmed Госуслуги account, СНИЛС in the profile, parent linked in the regional register) as the way in; the local passport login is still advertised on one.umnik-zo.ru and one.edu87.ru but was last exercised in code against 43edu in May 2024.

*cookie injection (X1_SSO)* — token carried as cookie X1_SSO. Lifetime: opaque; expiry raises 401 AuthExpiredError, no silent re-auth.

1. obtain X1_SSO from a logged-in browser (DevTools -> Application -> Cookies)
2. send Cookie: X1_SSO=<value> on every request to one.<region>.ru

   pskovedu-sdk Client.from_cookie (sessions/base.py _inject_cookies); tdrkDev parser copies raw Cookie header. PHPSESSID alone insufficient on pskovedu (redirects to /auth/login, confirmed by live testing per SDK docs). This is the SDK's recommended method in its June 2026 docs/authentication.md.

*ESIA headless OAuth2 replay (pskovedu-sdk, experimental, undocumented)* — token carried as cookie X1_SSO (+ Bearer JWT in SDK code only). Lifetime: JWT exp/iat; refresh skew 300s. Refresh: none that works: re-run the replay or re-inject a fresh X1_SSO.

1. GET passport.pskovedu.ru/auth/esia/redirect -> 302; capture Location
2. parse client_id, client_secret (DER/CMS blob leaked in Location query), state, redirect_uri
3. GET esia.gosuslugi.ru/aas/oauth2/ac?{params} -> ESIA cookies, follow to /login
4. POST esia.gosuslugi.ru/aas/oauth2/api/login form login (СНИЛС/email/phone), password, client_id, state, redirect_uri, client_secret, scope=openid, response_type=code (may return CAPTCHA)
5. follow 302 to passport.pskovedu.ru/auth/esia/return?code=&state= which sets X1_SSO
6. (SDK code only) AuthManager._obtain_jwt still calls GET https://one.pskovedu.ru/session, which commit 73d4ae6 (2026-06-20) proved does not exist (404 'Url could not be matched'); identity comes from X1_CONFIG.meta.au in the GET / shell instead

   Present in pskovedu/auth/esia.py + AuthManager.login_with_esia but not in the June 2026 docs/authentication.md, which lists only cookie injection and QR login. ESIA may answer with CAPTCHA (ChallengeRequired).

*QR login via Gosuslugi (ESIA), pskovedu-sdk* — token carried as cookie X1_SSO (from confirm response). Lifetime: 120s to scan or 3 qr-error events then AuthError.

1. POST esia.gosuslugi.ru/qr-delegate/qr/generate -> {qrId}
2. display QR URL one.<region>.ru/qr-delegate/qr/{uuid}
3. GET esia.gosuslugi.ru/qr-delegate/qr/subscribe/{uuid} (text/event-stream): waiting\|ping\|qr-error\|qr-auth-confirmed
4. on qr-auth-confirmed take one-time code
5. POST esia.gosuslugi.ru/qr-delegate/qr/confirm {code} -> {x1_sso}

   Modeled, not end-to-end verified; /qr-delegate/qr/confirm is flagged '# unverified' in constants.py. docs/known-issues.md (June 2026): SFD session-token exchange confirmed, full handshake not end-to-end verified. login_with_qr now returns the GET / shell (ShellConfig), not a /session profile.

*Selenium / WebView Gosuslugi login (Оренбургская)* — token carried as cookie — PHPSESSID on de.edu.orb.ru (edu-orb bot) OR X1_SSO on edu.orb.ru (Android tool). Lifetime: static session cookie.

1. open de.edu.orb.ru/login (or edu.orb.ru/auth/rsaag/redirect/?returnTo=https://edu.orb.ru)
2. click «Вход через ГИС ЕЛК» / ESIA
3. fill Gosuslugi login (id=login) + password (id=password), solve photo/text captcha (esia-captcha), enter 2FA code (input[type=tel])
4. keep the diary session cookie

   edu-orb.ru bot sends ONLY PHPSESSID to de.edu.orb.ru; DmitryKolyadin app reads X1_SSO from edu.orb.ru WebView and forwards it to its own Yandex Cloud bot endpoint (not part of the platform). The 2026 search index lists de.edu.orb.ru/auth/login as the Orenburg login page.

*ЕСИА via passport → X1_SSO → mobile login → initsession* — token carried as JSON body fields (sid = X1_SSO cookie value, apikey = encrypted session key); no Cookie or Authorization header is sent to mp2.

1. Open https://passport.obr57.ru/auth/esia/redirect/?returnTo=https://one.obr57.ru in a WebView with JavaScript, DOM storage and third-party cookies on; the user signs in on the real ЕСИА page
2. Read cookie X1_SSO from CookieManager on every onPageFinished (any URL) and on every shouldOverrideUrlLoading whose URL contains obr57.ru or shkolove.ru; ignore empty or 'deleted'; then removeAllCookies + flush and hand the token to Rust
3. POST https://mp2.obr57.ru/journals/login {sid: X1_SSO, api_key: ahh_encrypt(X1_SSO)} → profile; success=false → rejected with message; parent if ROLES contains 'parents'/'parent' (case-insensitive), USER_PARTICIPANTS non-empty, or PARENT present; a parent with several USER_PARTICIPANTS picks a child, one child is connected directly
4. POST https://mp2.obr57.ru/session/initsession {sid: ahh_encrypt(X1_SSO), apikey: <fixed 48-char app constant>, sysguid: ahh_encrypt(pupil GUID)} → {status, key}; empty key = rejection
5. Every data call: POST https://mp2.obr57.ru/journals/<route> {guid: pupil GUID plain, apikey: ahh_encrypt(key), pdakey: "<redacted>", sid: X1_SSO raw, ...route fields}
6. Switching child (lib.rs): call /session/initsession again with the stored raw X1_SSO and the new GUID, replace the key and clear the per-child caches; no refresh route exists — diaryday maps 401/403 to «Сессия истекла — войдите заново», the other data routes report any non-2xx as «Журнал не пускает»

   ahh_encrypt (rust/src/crypto.rs) = AES-128-ECB with PKCS#7 padding under a fixed 16-byte key (8 non-zero bytes followed by 8 zero bytes), output standard Base64 without line breaks; a reverse-engineered obfuscation of the official app, not a per-user secret. The client stores X1_SSO and the session key under Android Keystore envelope encryption (KEK in AndroidKeyStore, DEK AES-256-GCM). Login and initsession use a 10 s timeout, data routes 8 s.

**Headers the clients send.**

| Header | Value | Why |
| --- | --- | --- |
| `Cookie` | X1_SSO=<value> (or PHPSESSID=<value> on de.edu.orb.ru) | authenticates every portal REST / Ext.Direct call |

| `Content-Type` | application/json | for POST /extjs/direct and /x1db/service/call |
| `Accept` | application/json | diary/schedule/Ext.Direct JSON; pskovedu-sdk sends */* for byte (xls) downloads; report exports use format=xls\|html query param |

**Captcha and second factor.** ESIA (gosuslugi) login can present photo or text CAPTCHA and SMS/authenticator 2FA — handled by human via Selenium in edu-orb bot; pskovedu-sdk raises ChallengeRequired('captcha') and cannot solve it.

Two regional cookie conventions coexist: X1_SSO (Pskov, Kirov, Orenburg-via-edu.orb.ru) and PHPSESSID (Orenburg-via-de.edu.orb.ru). All regions front the portal with passport.<region>.ru or edu.<region>.ru SSO supporting local login/password (СНИЛС) and ESIA/Госуслуги. As of September 2026: all X1 instances front ESIA; from 1 Sep 2026 parents and students are directed to «Госуслуги Моя школа» (app, gosuslugi.ru/school, Сферум/MAX widget) for the diary, which is a different platform; the X1 portals remain the regional journal. No app-only token or new captcha on the X1 side is documented.

**Formats.**

- *Dates*: DD.MM.YYYY throughout query strings and JSON (e.g. date=01.09.2025). Diary JSON keys the week by weekday, sometimes 'DD.MM. Понедельник'. Lesson times are naive local wall-clock HH:MM strings. Session JWT exp/iat are unix epoch.
- *Ids*: Opaque uppercase-hex GUIDs (32 chars, no dashes), e.g. participant/grade/journal SYS_GUID = 'B22275F0B52B8A7663899CA8BF970212'. X1 ORM model SYS_GUIDs are installation-specific and resolved at runtime from X1_CONFIG.meta.models (NAME->GUID); they change per region. JournalState is a StrEnum whose values are the digit strings 1..4 (as JSON strings), sent as SYS_STATE.
- *Pagination*: Ext.Direct/X1 results return arrays or {data:[],total:N}; SDK wraps as EduPage[T].items or a PageIterator walking weeks/days by date. No offset/limit REST pagination on diary/schedule — re-request per date.
- *Notes*: Diary and report exports available as XLS (format=xls) and sometimes HTML (format=html, table#sheet0). Reports read via xlrd/pandas->csv in Two.Diary. Ext.Direct envelope: {action,method,data,type:'rpc',tid}; real X1API.direct wraps {service,method,params,ctx}. Schedule JSON keys are uppercase (SYS_GUID, NAME, LESSON_TIMES, NUMBER, TIME_BEGIN, TIME_END, LESSONS, SUBJECT, TEACHER, CLASSROOM, HOMEWORK).

**Refuted during verification** — rows an extractor proposed that no source carries, kept here so that nobody re-proposes them.

- GET `/session (https://one.pskovedu.ru)` — pskovedu-sdk commit 73d4ae6 (2026-06-20, 'fix: remove fictional portal /session endpoint'): live testing against one.pskovedu.ru got 404 'Url could not be matched'; GetSession, Client.get_session and PATH_SESSION were removed; only a leftover _SESSION_PATH in auth/manager.py still references it.
- ANY `https://one.astrobl.ru/* (Астраханская область as an X1 instance)` — one.astrobl.ru is a white-labelled ЭлЖур: indexed titles «Цифровое образование — Электронный журнал — Цифровое образование» and «Помощь — Электронный журнал — Цифровое образование» follow ЭлЖур's '<page> — Электронный журнал — <org>' pattern (as on attestatus.eljur.ru, amk.eljur.ru in Astrakhan), and the host serves ЭлЖур's /authorize and /journal-help-action paths (cf. chesu.eljur.ru/authorize, mvd1.eljur.ru/journal-help-action) plus /dooservice/queue. **Caveats.**

- pskovedu-sdk is self-described 'vibe-coded' and its own docs/known-issues.md marks every Ext.Direct, X1 ORM, EJE, report, avatar, oauth-config, check-auth and the QR/ESIA handshake as UNVERIFIED. Only GET /edv/index/diary, its XLS, marks-report, GET /schedule/index/schedule and /current are marked verified. The SDK explicitly says its flat /extjs/direct envelope is WRONG (real shape is X1API.direct wrapping {service,method,params,ctx}); treat all Ext.Direct rows as best-effort.
- /x1db/service/call is where the SDK's X1Protocol posts, but the SDK's own architecture doc says the portal JS defines one RemotingProvider at /extjs/direct with the single action X1API.direct; the separate /x1db path has no capture behind it.
- The SDK's code and docs disagree on /session: AuthManager._obtain_jwt still calls GET {portal}/session (auth/manager.py), which commit 73d4ae6 removed everywhere else after it 404'd live ('Url could not be matched'); POST sfd.gosuslugi.ru/session appears only in docstrings and docs, and PATH_SFD_SESSION is never used.
- The /edv, /schedule, /report REST paths are proven identical only on 43edu.ru, pskovedu.ru and de.edu.orb.ru; assumed (not verified) on umnik-zo.ru, stavminobr.ru, edu87.ru.
- Two cookie regimes: X1_SSO (Pskov, Kirov, Orenburg-via-edu.orb.ru) vs PHPSESSID (Orenburg-via-de.edu.orb.ru bot). pskovedu-sdk asserts PHPSESSID alone is insufficient on Pskov. Which cookie a region requires must be checked per region.
- The Orenburg SSO host is edu.orb.ru (ESIA redirect) while the diary/API host is de.edu.orb.ru — do not conflate them.
- Diary lesson field names differ by region: Kirov (Two.Diary) reads lessonTimeBegin/lessonTimeEnd/periodMark; Orenburg (edu-orb) models a single lessonTime.
- Habr 806737 describes a different Kirov-region app using a natively-generated apikey, not the X1_SSO one.<region> platform; set aside.
- No PyPI or npm package exists for any of these hosts; Sourcegraph returns nothing for X1_SSO, one.43edu.ru, one.pskovedu.ru, de.edu.orb.ru, umnik-zo.ru, stavminobr.ru, edu87.ru or edv/index/diary. Everything is from source clones, an official PDF manual, and search results — no live API probing (all diary hosts unreachable; one.astrobl.ru answered WebFetch with 503).
- Region membership (after currency check): Кировская (one.43edu.ru), Псковская (one.pskovedu.ru), Запорожская (one.umnik-zo.ru), Оренбургская (de.edu.orb.ru) CONFIRMED; Ставропольский (one.stavminobr.ru) and Чукотский (one.edu87.ru) LIKELY on page-level evidence; Астраханская (one.astrobl.ru) REFUTED — it runs ЭлЖур.
- From 1 Sep 2026 federal policy moves parent/student diary access to «Госуслуги Моя школа» (kaspyinfo.ru 11.08.2026, 148chel.ru 19.08.2026; eanews.ru 01.09.2026 on Orenburg: «Проходит обновление системы «Электронный дневник» на платформе «Моя школа»»). The X1 portals are not replaced — they stay the regional journal behind ФГИС «Моя школа» — but a parent-facing client of /edv may lose its users or its access; nothing found says a specific X1 region closed the web diary to parents.
- The newest client, pskovedu-sdk, was written in a single day (all six commits 2026-06-20) and has no issues or users on record; its live-tested set is small (diary, diary XLS, marks-report, schedule, schedule/current).
- The QR confirm step as modeled (POST esia.gosuslugi.ru/qr-delegate/qr/confirm returning x1_sso) is implausible for ESIA to return a regional cookie; the real exchange presumably passes through passport.<domain>. Marked unverified by the SDK itself.
- All regional hosts (one.*, passport.*, de.edu.orb.ru) answered WebFetch with 403 or 503 in September 2026; everything about them comes from search-index titles, school pages and client code.
- No vendor API documentation exists: the portals name no vendor, and no public API document was found, so section 5 (documented routes) added nothing.
- Every mobile route comes from a single client (burmalda57); it is marked current because that client was committed in September 2026, but no second source confirms any of them.
- Whether Кировская, Псковская, Оренбургская and the other regions expose the same API on mp2.<domain> is NOT established: their official apps share the ru.integrics.* package family (kirovschool, mobileschool, mobiled, orelschool), which suggests one mobile codebase, but no code, document or page seen names their mobile host. No app for Запорожская, Чукотка or Ставропольский was found.

- The initsession apikey is a fixed application constant from a reverse-engineered official app; it may rotate with app versions and may differ per region. Its value is redacted here.
