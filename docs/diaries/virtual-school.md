# «Виртуальная школа» — Белгородская область, and Брянская until 2026

*Part of [the electronic diaries of Russia’s regions](../diaries.md). Verification: extracted and checked against the code, not yet dated. Confidence of the whole: low. Nothing here has been tried against the live service.*

**A vendor's diary run for several regions under their own names.** ИСОУ «Виртуальная школа»
(ООО «Медиа Сервис», app `ru.vsopen`) is Белгородская область's system at `vs.belregion.ru`, and
was Брянская's at `obr.b-edu.ru` until the region joined ТОР «Моя школа» on 1 September 2026;
`orel.vsopen.ru` still answers for Орловская, which has moved to the [«one.» platform](one-x1.md).
Older hosts under `<region>.vsopen.ru` carry the first generation, `/app`.

**Known from its own front end, not from a client.** No open client of the current system
exists. Its sign-in and API bases were read from the official web bundle as the Wayback Machine
archived it: OAuth2 with PKCE at `/auth/authorize`, a password or Госуслуги on the sign-in page,
tokens from `/auth/api/token`, then `Authorization: Bearer` with an `X-Api-Role` header naming the
role — parent, student or teacher — against `/app/api/2`. The screens that read the diary itself
were loaded lazily and never archived, so the rows under `/app/api/2` come from a staff screen and
say nothing yet about what a parent's view calls. Six rows are current, fourteen uncertain, and
the old `/app` generation — known from one 2023 scraper — is legacy.

**Signing in.**

*Current: OAuth2 authorization code + PKCE (vs.belregion.ru 2025-2026, obr.b-edu.ru 2026)* — token carried as Authorization: Bearer <access_token> header (plus X-Api-Role for the vs and college APIs); tokens live in the browser's localStorage, not cookies.

1. GET /config.json on the site origin; take auth_base_url, auth_api_base_url, client_id ('vsopen.ru/new'), redirect_url and hide_login_form.
2. Generate verifier = crypto.randomUUID(); code_challenge = base64url(SHA-256(verifier)) (crypto-js stringify of the digest, '+'->'-', '/'->'_', '=' stripped). Store the verifier in localStorage 'code_verifier'.
3. Open {auth_base_url}/authorize?client_id=vsopen.ru/new&code_challenge_method=S256&code_challenge=<challenge>&response_type=code&redirect_uri=<redirect_url>/services\|/schools\|/colleges (by current path; default /services)&scope=vs uslugi person_info notifications&state=<crypto.randomUUID()>, plus external=<?external from the page URL, else 'any'> when the page URL has ?external= or hide_login_form is 'true' (Белгород: true). Scope was 'vs uslugi person_info' in the 2025-03 and 2025-08 bundles.
4. The auth SPA (/auth) shows a login/password form that posts (HTML form, method post) login and password to {publicPath}/login, and a «Войти через Госуслуги» button that opens {publicPath}/login/esia. When the external value is 'esia' only the Госуслуги button is shown, with «По запросу системы, вход может быть произведен только через госуслуги.». A ?error= on the page is shown as the error text, or «Неправильный логин или пароль» when empty.
5. The auth server redirects back to redirect_uri with ?code=…; the SPA POSTs {auth_api_base_url}/token as application/x-www-form-urlencoded: code, code_verifier, client_id, grant_type=authorization_code. Response JSON {access_token, refresh_token} is stored in localStorage 'access_token' and 'refresh_token'.
6. GET {auth_api_base_url}/1/persons/me/authorization with Authorization: Bearer <access_token>; the SPA stores vsid (as 'id'), authType (as 'authMethod') and login.
7. API calls: fetchBaseQuery against api_uri (/app/api/2), api_uri_services, api_uri_college or api_uri_notifications, with Authorization: Bearer <access_token>, plus X-Api-Role: <role> for the 'vs' app (localStorage 'role') and the 'college' app ('roleSPO') when that role is not 'guest'. Roles: guest, parent, student, teacher.
8. On a 401 or 403 from any API call (except the endpoint named readRole) the call is queued and, after a 1 s debounce, the SPA copies the refresh token into the access-token slot and POSTs {auth_api_base_url}/public/token?client_id=vsopen.ru/new (no Authorization header; Content-Type application/x-www-form-urlencoded, Cache-Control/Pragma no-cache) with client_id, grant_type=refresh_token, refresh_token, code_verifier (the sign-in verifier, still in localStorage), scope. New {access_token, refresh_token} replace the old ones and the queue is retried; 400/401, a missing token pair or a network error signs out.
9. Sign out: open {auth_base_url}/logout?redirect_uri=<redirect_url or a path resolved against it>.

   All from the archived official bundles (main.20d52ba50789c191bb7b.js 2026-04, obr.b-edu.ru main.773575680a2f4f3d6918.js 2026-04, auth SPA main.aa1a343608d2aec9656c.js 2025-03). The auth SPA's {publicPath} comes from an axios GET of 'config' whose base was not archived; /auth is inferred from where the SPA is served. The diary endpoints under /app/api/2 were never archived.

*Superseded refresh (vs.belregion.ru bundle of 2025-03)* — token carried as Authorization: Bearer <refresh_token> on the refresh call; Bearer <access_token> otherwise.

1. On a 401 (except endpoints readProfileVS/readProfile/readRole) the SPA copies the refresh token into the access-token slot and POSTs '/token' through the same fetchBaseQuery, so the request carries Authorization: Bearer <refresh_token>.
2. For the vs app the base is auth_api_base_url (-> /auth/api/token); for services and college the base is api_uri_services / api_uri_college (-> https://uslugi.belregion.ru/api/2/token, …/college-app/api/2/token).
3. Body (x-www-form-urlencoded): client_id, grant_type=refresh_token, refresh_token, scope=vs uslugi person_info. Response read as camelCase {accessToken, refreshToken}; otherwise sign out.

   Replaced by /auth/api/public/token by the 2025-08 bundle. The 2025-03 bundle already used PKCE at /authorize and /auth/api/token for the code exchange.

*Old /app generation: password form (belgorod.vsopen.ru, bryansk.vsopen.ru, www.vsopen.ru)* — token carried as server session cookie (name not recorded in any source).

1. GET /app/login (or /app/login?loginerror&redirect_url=<widget>): HTML «Виртуальная школа :: Вход в систему» with form#login_form method=post and no action (posts back to the same URL).
2. POST fields: login (input#login_name), password (input#login_password), redirect (hidden, e.g. add/studentDiary).
3. On failure the server returns to /app/login?loginerror&redirect_url=… (bryansk also /app/login?message=Неправильный логин или пароль). On success the browser lands on /app/add/<widget> with a server session.
4. ScheduleVsopen (2023) drives exactly this with Playwright: fills id=login_name and id=login_password, clicks «Войти», then clicks «Дневник».

   Legacy. vs.belregion.ru's 2025-07 config has vsopen_old_enabled=false.

*Old /app generation: ЕСИА button* — token carried as server session cookie (name not recorded).

1. The old login page's «Войти через ЕСИА» button does location.replace('https://belgorod.vsopen.ru/app/esia?action=login&redirect=add/studentDiary').

   Legacy; also captured as www.vsopen.ru/app/esia and bryansk.vsopen.ru/app/esia?action=login.

*Old /app on the central auth server (vs.belregion.ru, 2025-03)* — token carried as server session cookie of /app (name not recorded).

1. GET https://vs.belregion.ru/app redirects (302) towards /app/oauth2/login.
2. /app/oauth2/login redirects to https://vs.belregion.ru/auth/authorize?response_type=code&client_id=vsopen.ru/app&scope=person_info id_token vs&state=<random>&redirect_uri=https://vs.belregion.ru/app/oauth2/login/callback (no PKCE parameters in the captured URL).
3. The server-side /app completes the code exchange itself at /app/oauth2/login/callback and keeps its own session.

   Only seen as Wayback CDX URLs (20250330035701, 20250330035445); bryansk.vsopen.ru and belgorod.vsopen.ru also had /app/oauth2/login in 2024.

*Old /app OAuth provider for partners* — token carried as authorization code in the redirect; partner-side exchange not recorded.

1. A partner sends the browser to /app/oauth/authorize?redirect_uri=<partner>&client_id=<id>&client_secret=<redacted>&state=…&response_type=code; captured caller: partners-api.algopartners.ru/virtual-school/v1/auth (ГТО).

   Legacy, captures 2022-08 to 2023-06 on belgorod.vsopen.ru (also vsopen.ru/app/oauth/authorize).

**Caveats.**

- Bundles were re-read from local copies fetched from the Wayback captures earlier in this research run (sg2/vsb); in this verification pass neither WebFetch ('unable to fetch from web.archive.org') nor curl (connection reset) could reach web.archive.org, so the byte-level identity of those copies with the captures was not re-established. Every literal quoted here was grepped from those copies.
- One open-source client exists, Asmoorr/ScheduleVsopen (2023): a Playwright screen-scraper of the old belgorod.vsopen.ru/app diary. It has no HTTP API code; it commits one api/1 diary JSON response (temp.json: {entities:[{id:'<startDateMs>_<lessonId>_<scholarId>', scholar, eduPlanTemplate, school, schoolGroup, subject, subgroup, scheduled, number, startDate, stopDate, examType, room, theme, homework, individualHomework, homeworkFiles, individualHomeworkFiles, teacher, scores, previousLesson}], totalCount}) without the path it came from; that request is built in client/js/edu/diary/diary.js, which is not in the repository and has no Wayback capture.
- The current system (vs.belregion.ru; obr.b-edu.ru since January 2026) has no client at all. Sign-in and API bases come only from the archived official bundle; the diary screens live in lazily loaded chunks that were never archived, so no pupil- or parent-facing diary endpoint of /app/api/2 is known. The only /app/api/2 paths seen come from a staff grade-list page, and even their /app/api/2 prefix is an assumption because the axios base module was not archived.
- X-Api-Role values are guest/parent/student/teacher (enum in the bundle); it is omitted for guest and never sent to the services or notifications APIs.
- The auth SPA's publicPath (hence the /auth prefix of /login and /login/esia) comes from an axios GET of 'config' whose base URL is not in the archived bundle.
- /.well-known/openid-configuration on both hosts was captured as text/html, most likely the SPA's fallback page rather than an OIDC discovery document.
- The partner OAuth capture exposes a client_secret in the query string; it is redacted here.
- Correction to the input (/app/add/studentJournal, /app/add/reports as sibling widgets in temp.html): temp.html's menu carries schedulingLesson, eduplans, thematicplans, messaging, notifications, studentDiary, studentportfolio, studentReport and start; studentJournal appears there only as a CSS path, and add/reports only as a redirect_url in the CDX. Corrected in the studentDiary route's notes.
- Correction to the input (/app/login (title «VSopen.ru :: …», windows-1251)): The archived login page is utf-8 and titled «Виртуальная школа :: Вход в систему»; «VSopen.ru :: Виртуальная школа» is the title of the saved diary page temp.html. Corrected.
- Correction to the input (/auth/api/1/persons/me/authorization (response person{…} and role per app)): The bundle's setAccountData reads only vsid, authType and login from this response; person and role are stored by code in unarchived chunks. Corrected.

Corrected.
