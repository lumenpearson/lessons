# «Моя школа» — the МЭШ platform deployed for the regions

*Part of [the electronic diaries of Russia’s regions](../diaries.md). Verification: extracted, checked against the code, and dated. Confidence of the whole: medium. Nothing here has been tried against the live service.*

**This is the system behind the app in the screenshot.** «Моя Школа» asks «Выберите регион»
and then talks to that region's own node of the Moscow МЭШ stack. Московская область runs the
reference node, `authedu.mosreg.ru`, with `myschool.mosreg.ru` as its web front; the other
nodes the vendor's own help page lists are Калужская (`education.admoblkaluga.ru`),
Татарстан (`ms-edu.tatar.ru`), Дагестан (`myschool.05edu.ru`), Тюменская (`myschool.72to.ru`),
ЯНАО (`school.yanao.ru`), Карелия (`karelia.minedu.ru`), Вологодская (`dnevnik.edu35.ru`),
Башкортостан (`dnevnik.edurb.ru`), Тверская (`dnevnik.tvobr.ru`) and Мурманская
(`edu.mso51.ru`). The routes are the МЭШ family API — `/api/family/mobile/v1`,
`/api/family/web/v1` — and a client for [МЭШ](mesh-moscow.md) needs mostly a different host.

**Signing in is Госуслуги, in a browser.** Regional accounts sign in through ЕСИА only, and the
node hands back an `aupd_token` JWT after its own code exchange at `/v3/auth/token`. The
headless ЕСИА login that OctoDiary-py scripted in 2023–2024 — MFA, security question, image
captcha and all — is listed, but nothing has confirmed it since, and ЕСИА changes without
notice. What works today in every client is the person signing in once in a browser and the
client keeping the token.

**What is thin.** Every row was read against `authedu.mosreg.ru`; for the ten other nodes only
the host is known, and whether each one exposes the full family API is inferred rather than
seen. The older `api.myschool.mosreg.ru/family/mobile/v1` spelling is kept as a note, because
the official app and the newer clients have moved to `authedu.mosreg.ru/api/family/mobile/v1`.

**Signing in.**

*Official browser sign-in (password «kauth» or Госуслуги «esia») -> code -> aupd token (official app, OctoDiary-kt since 2026-05, OctoDiary v4)* — token carried as header Authorization: Bearer <JWT> and/or Auth-Token: <JWT> (per endpoint, see required_headers); cookie aupd_token only in browser-captured sessions. Lifetime: JWT exp claim; not stated in code (OctoDiary-tg refreshes when under 3 days remain).. Refresh: POST https://authedu.mosreg.ru/v3/token/refresh form refresh_token=<refreshToken> -> 201 {access_token, refresh_token} per the vendor spec embedded in the app (regional use not observed); per-role re-issue via GET /v2/token/refresh?subsystem=2&roleId=. OctoDiary-kt performs no refresh for MySchool and asks the user to sign in again..

1. Generate state = uuid v4. Open in a browser/Custom Tab https://authedu.mosreg.ru/v3/auth/kauth/login?redirect_url=<scheme>://authRegionRedirect&state=<uuid> for login + password, or …/v3/auth/esia/login?… for Госуслуги (the help page tells regional parents and pupils to use Госуслуги only). Scheme: dnevnik-mes (official app build, OctoDiary-kt) or dnevnik-myschool (OctoDiary v4).
2. Catch the deep link <scheme>://authRegionRedirect?code=<code>.
3. GET https://authedu.mosreg.ru/v3/auth/token?code=<code>&state=<uuid> (no auth) -> 200 JSON {token, refreshToken}. The token is the aupd JWT; the official app rejects it unless it carries a role claim; a 404 means keep the stored token.
4. GET https://authedu.mosreg.ru/api/ej/acl/v1/mod-acl/users/profile_info with Auth-Token: <JWT>, Authorization: Bearer <JWT>, Partner-Source-Id: MOBILE, x-mes-subsystem: familymp -> [{id, type}] (OctoDiary-kt still uses GET https://myschool.mosreg.ru/acl/api/users/profile_info with auth-token and partner-source-id: MOBILE).
5. If several profiles: for each, GET https://authedu.mosreg.ru/v2/token/refresh?subsystem=2&roleId=<1 student \| 2 parent> with Authorization: Bearer <JWT> -> 201, text body = token for that profile. With one profile the app keeps the token and uses the parent profile if present.
6. Call the API with the profile's token and Profile-Id = its id.

   Logout after a Госуслуги sign-in (Android): open https://esia.gosuslugi.ru/idp/ext/Logout?client_id=500108&redirect_url=https://authedu.mosreg.ru/v3/redir?url=<scheme>://authRegionLogout. The JWT iss is https://authedu.mosreg.ru for this region (OctoDiary v4 detects the region from it). fgis-dnevnik-desktop does the same browser step on https://{node}/v3/auth/esia/login and captures the aupd_token cookie instead of using a deep link.

*LEGACY: headless login + password -> aupd_token cookie (OctoDiary-py, Mag329 fork; removed from OctoDiary-kt on 2026-05-12)* — token carried as Cookie aupd_token (set by /v3/auth/kauth/callback); afterwards sent as header Authorization: Bearer <JWT> + header Auth-Token: <JWT> + Cookie: aupdtoken=<JWT>; aupd_token=<JWT> (OctoDiary-py sends all three on every call). Lifetime: JWT with exp claim; OctoDiary-tg refreshes when less than 3 days remain (jwt.decode, exp). MESH_Helper treats exp-60s as invalid. Exact lifetime not stated in code.. Refresh: GET /v2/token/refresh with the bearer token (OctoDiary-py sends it to https://myschool.mosreg.ru; the official app to https://authedu.mosreg.ru with subsystem=2&roleId=)..

1. POST https://authedu.mosreg.ru/lms/api/sessions with JSON {"login": <login>, "password_plain": <password>}, header Accept: application/json, no token. Response is the SessionUserInfo object: id, email, snils, guid, person_id, first/last/middle_name, phone_number, profiles[{id,type,roles,user_id,agree_pers_data,subject_ids,organization_id,school_id,school_shortname,person_id,user_id}], authentication_token, password_change_required, regional_auth, sso_id.
2. GET https://authedu.mosreg.ru/v3/auth/kauth/callback?code=<authentication_token> without a token. The response Set-Cookie carries aupd_token=<JWT>; that JWT is the API token for everything else (also called «auth-token»/«access_token»).
3. (Recommended by OctoDiary-kt as a REQUIRED final step) GET https://myschool.mosreg.ru/acl/api/users/profile_info with auth-token: <JWT> and partner-source-id: MOBILE — «Token that haven't been used in this request is not eligible for other requests»; it returns the list of profile ids [{id,type}], and the first id becomes the profile-id header value.

   Superseded by the browser kauth flow above: OctoDiary-kt «Fix MySchool» (5284e5d, 2026-05-12) deleted enterCredentials (/lms/api/sessions) and exchangeToken (/v3/auth/kauth/callback); the official app has no /lms/api/ path. The web UI variant of the same thing is GET https://authedu.mosreg.ru/v3/auth/kauth/login?redirect_url=dnevnik-mes://authRegionRedirect&state=<uuid> (OctoDiary-kt) or redirect_url=dnevnik-myschool://authRegionRedirect (OctoDiary v4) opened in a Custom Tab/WebView; the deep link comes back with ?code=<code>, and the app exchanges it with GET https://authedu.mosreg.ru/v3/auth/token?code=<code>&state=<same uuid> → {"token": <JWT>, "refreshToken": <string>}. The JWT iss claim is https://authedu.mosreg.ru for this region (https://school.mos.ru for Moscow) and OctoDiary v4 uses it to detect the region; it also carries a personId/sso/exp claim (OctoDiary Examples decode «sso» from it).

*UNVERIFIED SINCE 2024: headless ЕСИА / Госуслуги login -> aupd_token (OctoDiary-py esia_login / esia_enter_MFA / Captcha)* — token carried as Cookie aupd_token on the authedu.mosreg.ru redirect; then Authorization: Bearer / Auth-Token / Cookie aupd_token as above. Lifetime: same JWT as the password flow. Refresh: same as the password flow (GET /v2/token/refresh).

1. Open a cookie-jar session. GET https://authedu.mosreg.ru/v3/auth/esia/login with allow_redirects=False; the body is an HTML meta-refresh «0;url=<esia authorize URL>», extracted with regex r"0\;url\=(.*?)\">" and followed (GET) to land on esia.gosuslugi.ru with the OAuth state in cookies.
2. GET https://esia.gosuslugi.ru/aas/oauth2/config (warm-up, sets cookies).
3. POST https://esia.gosuslugi.ru/aas/oauth2/api/login JSON {"login": <phone/email/СНИЛС>, "password": <password>}. Response JSON has action or failed: DONE → follow redirect_url; GRANT_SCOPE_ACCESS → POST https://esia.gosuslugi.ru/aas/oauth2/api/scope/allow and re-dispatch on its action; ENTER_MFA → mfa_details {type: SMS\|TOTP…} stored, caller must supply a code; SOLVE_ANOMALY_REACTION → reaction_details {type, guid}: type «О.ЗД1» is an image captcha, «О.ЗИ1» is a security question; any other value is raised as APIError.
4. (octodiary 0.2.5 only) action FILL_MFA — the «подключите вход с подтверждением» promo: POST https://esia.gosuslugi.ru/aas/oauth2/api/login/promo-mfa/fill-mfa?decision=false, then GET the redirect_url from its JSON; that response's cookie aupd_token is the JWT. 0.3.0 dropped this branch (an unknown action now raises APIError).
5. MFA: POST https://esia.gosuslugi.ru/aas/oauth2/api/login/otp/verify?code=<sms code> when mfa_details.type == SMS, else /aas/oauth2/api/login/totp/verify?code=<totp>; response dispatched on action again.
6. Security question: GET https://esia.gosuslugi.ru/anomaly-resolver/api/reaction/question?guid=<guid> → question_text; POST https://esia.gosuslugi.ru/aas/oauth2/api/anomaly/question/answer {"answer", "guid"} → action.
7. Image captcha: GET https://esia.gosuslugi.ru/captcha/api/public/v2/type → {captchaType (default esiacaptcha), captchaSession}; GET https://esia.gosuslugi.ru/captcha/api/public/v2/image with header captchasession: <captchaSession> → PNG bytes; optional GET …/captcha/api/public/v2/renew (new session) and GET https://esia.gosuslugi.ru/captcha-audio-service/api/public/v2/voice (audio); POST https://esia.gosuslugi.ru/captcha/api/public/v2/verify JSON {"answer", "captchaType"} header captchaSession → {verify_token}; POST https://esia.gosuslugi.ru/aas/oauth2/api/anomaly/captcha/verify?guid=<guid>&verify_token=<verify_token> JSON {"verify_token","guid"} → action.
8. On action DONE: GET the redirect_url from the response (it points back to authedu.mosreg.ru); the final response's Set-Cookie carries aupd_token=<JWT>. Same activation step (/acl/api/users/profile_info) afterwards.

   Only OctoDiary-py (2023–2024) and its unchanged Mag329 fork drive Госуслуги's own SPA API; every client maintained in 2025–2026 opens /v3/auth/esia/login in a browser (see the first flow). OctoDiary-kt/v4 do the ЕСИА flow in a browser instead: GET https://authedu.mosreg.ru/v3/auth/esia/login?redirect_url=dnevnik-mes://authRegionRedirect&state=<uuid> (v4: dnevnik-myschool://authRegionRedirect), catch the deep link ?code=, then GET https://authedu.mosreg.ru/v3/auth/token?code=&state= → {token, refreshToken}. The official help says regional parents/students sign in only «через Госуслуги» after choosing the region (login = phone, e-mail or СНИЛС). The OctoDiary-py code handles ЕСИА error codes invalid_credentials, pswd_method_temp_locked, no_subject_found, no_attempts, expired, invalid_otp.

*Token pasted by the user (OctoDiary-tg «Вход по токену доступа», PyMyschoolApi selenium)* — token carried as header Auth-Token: <JWT> (+ X-mes-subsystem: familyweb for the web family API) or Authorization: Bearer <JWT>. Lifetime: same JWT. Refresh: GET /v2/token/refresh.

1. User signs in in a browser at https://myschool.mosreg.ru/ (PyMyschoolApi drives Chrome to https://myschool.mosreg.ru/diary/schedules/schedule and waits for the URL) and copies the auth_token / aupd_token cookie (a JWT matching ^[A-Za-z0-9_=]+\.[A-Za-z0-9_=]+\.[A-Za-z0-9_\-+/=]*).
2. The client validates it with jwt.decode(verify_signature=False) and uses it directly as auth-token / Bearer.
3. Alternative (Vercixx/wallSchedule guide): sign in at https://authedu.mosreg.ru/, then open https://authedu.mosreg.ru/v2/token/refresh?roleid=1&subsystem=2 in the same browser; the page body is the JWT.

   OctoDiary-tg's own hosted page https://octodiary.den4iksop.org/bot-auth-x/?tg_user_id=&system=myschool&method=web\|web-logpass\|token is a third-party helper, not part of the platform.

*Teacher web session (authedu.mosreg.ru teacher UI, MESH_Helper)* — token carried as Authorization: Bearer <JWT> plus profile-id, aid, x-mes-subsystem (teacherweb \| journalw \| journalsw), x-mes-hostid: 9, x-mes-roleid: 9. Lifetime: JWT exp; extension re-checks every few seconds. Refresh: not implemented in the extension.

1. The teacher signs in in the browser (same aupd JWT). The extension captures Authorization: Bearer <JWT>, profile-id and aid (academic year id) headers from any request to *://authedu.mosreg.ru/api/* via chrome.webRequest.onBeforeSendHeaders.
2. POST https://authedu.mosreg.ru/api/ej/acl/v1/sessions JSON {"auth_token": <JWT>} with headers authorization: Bearer <JWT>, profile-id, x-mes-subsystem: teacherweb, x-mes-hostid: 9, x-mes-roleid: 9 → {first_name,last_name,middle_name, profiles[{id,type}]}; a 401/403 here means the session expired.

   Teacher endpoints are under /api/ej/core/teacher/v1, /api/ej/plan/teacher/v1, /api/ej/report/teacher/v1; the x-mes-subsystem value differs per service (teacherweb for core/acl, journalw for plan/attendances, report tried with teacherweb→journalsw→journalw fallback).

**Captcha and second factor.** In the current browser flow the captcha, SMS/TOTP second factor and consent screens are Госуслуги's own pages and need a person. The headless OctoDiary-py flow (2023–2024, unverified since) handles ENTER_MFA (otp/totp at /aas/oauth2/api/login/{otp\|totp}/verify?code=), SOLVE_ANOMALY_REACTION (image captcha «О.ЗД1» via /captcha/api/public/v2/* + /aas/oauth2/api/anomaly/captcha/verify, security question «О.ЗИ1» via /anomaly-resolver/api/reaction/question and /aas/oauth2/api/anomaly/question/answer), GRANT_SCOPE_ACCESS (/aas/oauth2/api/scope/allow) and, in 0.2.5 only, FILL_MFA. The regional password page (/v3/auth/kauth/login) shows no captcha in any client that opens it.

As of 2025–2026 sign-in is browser-only: /v3/auth/kauth/login (password) or /v3/auth/esia/login (Госуслуги) -> deep link code -> /v3/auth/token. The official help page says regional parents and pupils sign in only «через Госуслуги»; the official app still has the password mode («password auth»). Two independent id spaces are used everywhere: profile_id / student_id (integers, from profile_info and family profile children[].id) and person_id / contingent_guid (UUID string, children[].contingent_guid, used by eventcalendar, rating, persondata, avatars, day-balance-info/v2, meals/v2). class_unit_id (int) identifies the class. Every OctoDiary-py request funnels through one headers() builder, so the Authorization + Auth-Token + cookie triple is always present; the Kotlin clients prove that a single one of them (auth-token or Bearer, per endpoint) is enough. Errors come back as JSON {type, description, details}; OctoDiary-py raises for status > 400 only, and «Рейтинг не доступен.» in a 4xx body of /api/ej/rating/v1/rank/class means rating is switched off for the school rather than an auth failure. No rate limiting is handled in any client.

**Formats.**

- *Dates*: Query dates are ISO yyyy-MM-dd (from/to, begin_date/end_date, date, beginDate/endDate, onDate, dates=…%2C…); OctoDiary-py formats them in MSK (UTC+3) and datetimes as yyyy-MM-ddTHH:mm:ss; day-balance-info/v2 «from» is an ISO datetime with milliseconds and Z (yyyy-MM-ddT00:00:00.000Z). Response timestamps are ISO with time (created_at, updated_at, point_date, birth_date). The teacher API (/api/ej/plan\|core/teacher/v1) uses DD.MM.YYYY for from/to/start_at/stop_at. JWT exp is a Unix timestamp.
- *Ids*: Two id spaces: integers (profile id from /acl/api/users/profile_info, student_id = children[].id, user_id, class_unit_id, class_level_id, school_id, subject_id, group_id, mark id, lesson/event id, homework_entry_id, academic_year_id/aid, organization_id) and UUID strings (person_id = contingent_guid, guid, sso_id, material uuid, avatar person_id). Region is encoded in the JWT iss claim (https://authedu.mosreg.ru) and by numeric region codes in clients (50 Московская, 77 Москва, 40 Калужская, 16 Татарстан, 05 Дагестан, 72 Тюменская, 95 Чечня, 89 ЯНАО). Header names are case-insensitive but code spells them x-mes-subsystem / X-Mes-Subsystem / X-mes-subsystem interchangeably.
- *Pagination*: Mostly none: date ranges bound the result. page/per_page on /core/api/student_profiles, /core/api/profiles (clients pass per_page=1000 or 2147483647 to disable paging), /v1/nsi/organisations (page/size), teacher endpoints (page/per_page up to 1000), /family/mobile/v1/day_balance_info (first/after cursor) and day-balance-info/v2 (limit). Mobile list responses are wrapped in {payload: [...]}; eventcalendar in {total_count, response: [...], errors}; several web endpoints return bare JSON arrays.
- *Notes*: Booleans in query strings are rendered as true/false and None as null by OctoDiary-py. Errors are {type, description, details} JSON; clients treat status > 400 as APIError, 401 as expired token, and an empty profile_info array as an expired token. Rating endpoints use camelCase (personId, classUnitId, rankPlace, averageMarkFive) while the family API uses snake_case. The official app expects 201 Created (not 200) from /v2/token/refresh and /v3/token/refresh.

**Caveats.**

- Everything is reverse-engineered from unofficial clients; there is no published API documentation for authedu.mosreg.ru / myschool.mosreg.ru. The only official document read (help page) describes the browser login, not the API. The strongest evidence is the official app's own bundle (decompiled), which is vendor code but not documentation.
- The mobile family API is at https://authedu.mosreg.ru/api/family/mobile/v1/* (official app, OctoDiary-kt since 2025-02, OctoDiary v4); the older https://api.myschool.mosreg.ru/family/mobile/v1/* spelling is kept only as a note. Likewise /v2/token/refresh is called on myschool.mosreg.ru by OctoDiary-py and on authedu.mosreg.ru by OctoDiary-kt. Neither could be probed live from this session; both are reported as seen.
- OctoDiary-py (the richest client) last changed in May 2024 and the OctoDiary-kt README says development moved to the v4 repository, whose regional support beyond Moscow region is TODO (MesTatarstanAuthGateway, checkToken, refreshToken not implemented). Endpoints seen only in OctoDiary-kt (homework done/undone, marks/{id}, day-balance-info/v2, meals/v2/*, portfolio govexams, avatarmanagement, ej/partners launch, /v3/auth/token) have a single source. Since then the official app bundle independently confirms /v3/auth/token, /v2/token/refresh, day-balance-info/v2, ej/partners launch, rank/*, usersettings and the /homeworks/{id}/done pair.
- The teacher API (/api/ej/acl\|core\|plan\|report/teacher/v1) comes from one browser extension (MESH_Helper) that reuses the web UI's own bearer token; it is written for one school and hard-codes aid values 13/14 and x-mes-hostid/x-mes-roleid = 9. Response shapes for those routes are inferred from field accesses, not models.
- For the ten other regional instances (Калужская, Татарстан, Дагестан, Тюменская, ЯНАО, Карелия, Вологодская, Башкортостан, Тверская, Мурманская) only the entry hostnames are known (official help page). Apart from fgis-dnevnik-desktop on dnevnik.edurb.ru, no open-source client or package calls any of them (the official ru.mes.dnevnik string table names five hosts with an /api/family/mobile base, see regional_instances), so whether they expose the same /api/family/*, /api/eventcalendar/*, /v3/auth/* paths is an assumption from the shared МЭШ stack, not an observation. The only known differences are the ЕСИА-only login (no regional login/password documented) and, for ЯНАО and Тверская, an /esia/ entry path. Update: for Калужская, Татарстан, Дагестан and Тюменская the official app region table gives the same four-host layout as Московская область (authBaseUrl = apiSchoolUrl = entry host, apiMapiUrl = entry host + /api/family/mobile/v1, a separate web «dnevnik» host).
- The ЕСИА endpoints on esia.gosuslugi.ru are Госуслуги's own and change independently of the diary; the OctoDiary-py implementation dates from 2023–2024.
- No rate limits, retry rules or User-Agent requirements are enforced in any client; OctoDiary-py merely randomises the User-Agent. The mos.ru (Moscow, school.mos.ru) OAuth routes shared by the same code were deliberately left out of the table.
- The official ru.mes.dnevnik app's string table shows that the Moscow app itself carries per-region base URLs (https://{host}/api/family/mobile for five regional hosts), which supports — but does not prove path by path — the assumption that regional instances expose the same family-mobile API.
- /v3/token/refresh is now in the table as POST https://authedu.mosreg.ru/v3/token/refresh (form refresh_token, 201 {access_token, refresh_token}) from the vendor spec and generated client inside the official app; no regional saga was seen calling it, so it stays «uncertain».
- SolomonNumb1/fgis-dnevnik-desktop lists ~80 «myschool.<region>» hosts; most of them are not confirmed by the official help page or the official app strings and were not added to regional_instances.
- Currency is established from code, not from live traffic: the official ru.mes.dnevnik bundle (decompiled Hermes, AmetistYT/mesh_expressive; region table, auth sagas, generated clients), OctoDiary-kt history (2025-02 host move, 2026-05 login rewrite) and one user report (403 from api.myschool.mosreg.ru, Sept 2025). No host could be probed from this session.
- The official app region table lists only five regions with hosts (40, 50, 16, 5, 72); ЯНАО (189) and Чечня (195) exist only as ids, and the 2026/27 nodes (Карелия, Вологодская, Башкортостан, Тверская, Мурманская) appear only on the help page. For them the same /v3/auth/* and /api/family/* paths are an assumption from the shared stack; only dnevnik.edurb.ru has third-party client evidence (fgis-dnevnik-desktop).
- The official app embeds vendor OpenAPI specs (stoplight: «Запросы school.mos.ru», family/mobile/v1, ej/rating/v1, portfolio, meals v3 …) written against school.mos.ru servers; they belong to Moscow МЭШ (mesh_moscow) and were not copied here, except POST /v3/token/refresh whose generated client is shared by the regional auth code. Which of those services each region enables is decided by remote config the bundle does not contain.
- Moscow-only services (visits/turnstiles, family status, meals v1/v2 clients, day_balance_info v1, uchebnik.mos.ru token exchange) were removed; day-balance-info/v2 and meals/v2/menu/complexes stay «uncertain» because nothing marks them Moscow-only, but nothing shows them answered in the region either (Московская область meals live at food.myschool.mosreg.ru).
- The previous Московская область diary, school.mosreg.ru / api.school.mosreg.ru / login.school.mosreg.ru, was a Дневник.ру white-label; its routes were moved out (see refuted) and belong under the Дневник.ру platform.
- No vendor-published API documentation exists for the regional nodes; the help pages (help.myschool.mosreg.ru answered 503, mirror myschool.mos.ru/help) document only the browser sign-in and the list of eleven regional entry hosts.
