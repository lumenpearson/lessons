# eSchool — «Электронная школа», eschool.center

*Part of [the electronic diaries of Russia’s regions](../diaries.md). Verification: extracted, checked against the code, and dated. Confidence of the whole: medium. Nothing here has been tried against the live service.*

**A commercial diary of ООО «ИТ-Стратегия» (Санкт-Петербург), sold to schools rather than to
regions.** One SaaS instance, one API at `app.eschool.center/ec-server`, used by the web client
and the official mobile app alike. It appears in no region's survey as the regional system; a
school that bought it is an exception inside its region, which is why it gets a page and no row
in [the regions](regions.md).

**Signing in is a login and a password**, and the session is the `JSESSIONID` cookie. The login
answers with code 3 when it wants a captcha, and no client solves one. reSchool-flutter
(September 2026) is the only maintained client and carries most of the rows; where it and the
2020 client disagree — `getDiaryPeriod_` against `getDiaryPeriod`, `PUT chat/messages` against a
GET — the current spelling is marked current and the old one legacy.

**Hosts.**

**Signing in.**

*Login + password (the only flow)* — token carried as cookie JSESSIONID. Lifetime: server session; state.user.sessionEnd / validForDays are returned (eSchool_JS types) but no client reads them; reSchool's server keeps it alive with /events (reconnect after 5 s) + /news/digest every 200 s. Refresh: none; the reSchool app logs in again with stored credentials on 401 (recovery throttled to once per 30 s); reSchool's server keep-alive never re-logs in by itself and waits for the user; eschool_py re-runs auth() on every 401.

1. Compute lowercase hex SHA-256 of the password
2. POST https://app.eschool.center/ec-server/login, form fields username, password=<sha256>, device=<JSON {cliType,cliVer,pushToken,deviceId,deviceName,deviceModel,cliOs,cliOsVer}>
3. Take JSESSIONID from Set-Cookie (success = 200 with the cookie or a body longer than 5 chars; failure = body integer 1 wrong credentials, 3 captcha required, 4 account blocked)
4. GET /ec-server/state with the cookie: read userId, user.prsId, user.currentPosition (posTypeCode 'S' student, 'P' parent) and profile
5. For a parent: pick the child from user.currentPosition.myChildren (isDefaultChild), use the child's prsId and the userId of its current enrollment (userData[] with fullStartDate<=now<=fullEndDate, else yearState 'CURR')
6. Resolve class and period: usr/getClassByUser?userId -> groupId; dict/periods/0?groupId -> items[].id = eiId; profile/getProfile_new?prsId -> max pupil[].yearId for getPupilUnits/getLPartListPupil

   No ЕСИА/Госуслуги and no OAuth seen in any client. Captcha (code 3) is not handled by any client. As of September 2026 nothing indicates a change of flow; the official app 8.3.0 added password recovery (route unknown).

**Headers the clients send.**

| Header | Value | Why |
| --- | --- | --- |
| `Cookie` | JSESSIONID=<session> | the only credential |
| `User-Agent` | eSchoolMobile | reSchool imitates the official mobile app on every call (api_service _userAgent, server config USER_AGENT) |
| `Origin` | https://app.eschool.center | sent by reSchool on every call, as the web client does |
| `Referer` | https://app.eschool.center/ (app); https://app.eschool.center/Private/student/diary/1 (server keep-alive) | sent by reSchool on every call |
| `Content-Type` | application/x-www-form-urlencoded (login); application/json;charset=UTF-8 (PUT chat/student bodies); multipart/form-data (sendNew, updateMessage) | per endpoint |

**Captcha and second factor.** Login answers code 3 when a captcha is required; no client solves it. No SMS or 2FA seen, and none mentioned on the vendor's pages.

The device.cliVer reSchool sends is the current Google Play version of the official app (fetched by .github/scripts/fetch_eschool_version.mjs / AppConfig.eSchoolVersionUrl, fallback 8.1.0); device model is picked from assets/devices.json and push token/deviceId are random — the clients evidently expect the server to look at the client version. eschool_py (2020) logged in without the device field at all; eSchool_JS sends a non-JSON literal and still got a cookie in 2024. Currency check (2026-09): reSchool 2.0.3 _performLogin is unchanged (SHA-256 + device JSON, then /state); its optional 'cloud session' reuses a JSESSIONID stored on reSchool's own server and validates it with GET /ec-server/state — a client feature, not an eSchool flow. Vendor pages (eschool.center /, /about, /resheniya/, /vozmozhnosti/, /support/) mention no Госуслуги/ЕСИА, SMS or 2FA. The official app 8.3.0 (RuStore, 2026-09-20) lists «восстановление пароля» as new; no client carries a password-recovery route, so its path is unknown.

**Formats.**

- *Dates*: Epoch milliseconds almost everywhere (d1/d2, begDate/endDate, date, sendDate, date1/date2); some objects also carry *Str strings (date1Str, begDateStr); getProfile_new uses date strings (birthDate, issueDt)
- *Ids*: Integer ids: prsId (person), userId (a person's account within an organization/year; differs from prsId, and a parent's child has its own), orgId, groupId (class), eiId/period id, unitId (subject), lessonId, partId, variantId, threadId, msgId, msgNum, fileId, yearId
- *Pagination*: Chat lists page by rowStart/row + rowsCount, plus msgStart (messages) or msgNum (threads) cursors; news/digest uses page/pageSize; diary endpoints are ranged by d1/d2 or by period eiId
- *Notes*: Most student endpoints wrap lists in {result:[...]}; chat endpoints return bare arrays or bare integers. Homework text is HTML; images inside it are relative to https://app.eschool.center/. Trailing slash matters to the clients: getDiaryUnits/ and getDiaryPeriod_/ are called with it.

**Caveats.**

- No official public API documentation exists; everything is reverse-engineered from the web/mobile client by three open-source projects.
- reSchool-flutter (last commit 2026-09-18) is the only actively maintained client and carries most of the routes; eSchool_JS (2024-03-03, npm eschoolapi 0.8.1) is small; eschool_py (2020-09-10, PyPI eschool 1.3.0 = repo, eschool-py 0.9 = older copy with hard-coded userId 108217) is unmaintained.
- Routes seen only in eschool_py (student/diary, usr/olist, chat/mem_and_cnt, GET chat/messages, GET chat/sendNew, files/{id}) may no longer exist; the maintained clients use PUT chat/messages and POST chat/sendNew instead.
- student/getDiaryPeriod/ (eSchool_JS, eschool_py) versus student/getDiaryPeriod_/ (reSchool 2026): the underscore spelling is the one in current use; whether the old one still answers is unknown.
- No teacher-side (journal) endpoints appear in any client; all routes are pupil/parent views.
- Which regions or schools use eschool.center is not published by the vendor; the only concrete schools in code are Saint Petersburg ФМЛ № 30 and ФМЛ № 239 (reSchool presets). It is a commercial SaaS chosen per school, not a regional state system.
- reSchool's own backend (/proxy, /proxy/version, /custom-homework/*, /homework/analysis, /textbook/*, cloud-session store) is not part of eSchool and is excluded from the route table.
- The verifier found no fourth client: GitHub repository searches, npm, PyPI and Sourcegraph return only the three already read.
- Nothing was verified against the live host: diary hosts are unreachable from this environment.
- Currency (2026-09): the API has a single generation (/ec-server on app.eschool.center); reSchool 2.0.3 of 2026-09-18 uses it unchanged, and the official app is maintained (8.3.0, 2026-09-20). No move to ФГИС «Моя школа» or ЕСИА was found for this commercial platform.
- The official app 8.3.0 added password recovery and teacher-side grading features whose endpoints no open client carries; the route table covers pupil/parent views only.
- Routes seen only in eSchool_JS (2024-03: groups/getGroupOnly, chat/privateThreads, student/getDiaryPeriod/) are not re-confirmed by the 2026 client; getGroupOnly and privateThreads stay 'current' because nothing replaced them, getDiaryPeriod/ stays 'uncertain' because reSchool switched to getDiaryPeriod_/.
- Name collision: «Электронная школа»/eSchool (eschool.center) is not ЭлШкола (elschool.ru) nor Nsity/eschool (a self-hosted project); none of their routes are in this table.
- Which schools use eSchool could not be established beyond the two Saint Petersburg lyceums: the vendor publishes no list and the session's web search budget was exhausted.
