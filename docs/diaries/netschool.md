# «Сетевой город. Образование» — ИРТех

*Part of [the electronic diaries of Russia’s regions](../diaries.md). Verification: extracted, checked against the code, and dated. Confidence of the whole: medium. Nothing here has been tried against the live service.*

**This project now reads «Сетевой город» server-side, from this page.** `server/app/providers/netschool/` implements the password flow of the section below — `GET /webapi/logindata` to check the region takes a password, `POST /webapi/auth/getdata` for the one-shot salt, the windows-1251 salted MD5 into `POST /webapi/login` (with the staff-and-parent role re-login), then the bootstrap (`student/diary/init`, `years/current`, `context`, `grade/assignment/types`), the weekly `student/diary` walk with homework as assignment `typeId == 3`, `schools/search` for binding a class, `terms/search` for the academic periods, and `POST /webapi/auth/logout` on sign-out. Sessions are held open from the cron tick with `GET /webapi/context`. The regional servers it will ever contact are a fixed allow-list (`app/providers/netschool/regions.py`) — nothing from a client, a class row or a stored credential ever becomes a URL — over `https` only, and the ЕСИА-only rows in it are marked `password=False` and never offered. The `at` bearer, the cookies and the salted password travel only in headers and form bodies, never in a URL, because this deployment logs every request URL. **None of it has been run against a live server**; it is written from the open clients surveyed here and exercised on hand-written payloads, the same caveat Петербург carries (#121, #135).

**One product, one route set, a different server in every region.** Each regional
installation — `asurso.ru` in Самарская, `giseo.rkomi.ru` in Коми, `sgo.e-mordovia.ru` in
Мордовия and some fifty more listed below — runs the same `/webapi` JSON API, at whatever
version the region last upgraded to. The table is therefore a union across versions 4.x to
5.32, and a row may be missing from an older server; `GET /webapi/logindata` answers with the
version. A client finds the school with `/webapi/schools/search` and is otherwise the same
everywhere.

**It is the main diary of twenty regions in September 2026, and was of more.** Чувашия,
Краснодарский край, Алтай, Костромская and Челябинская left it for ТОР «Моя школа» on
1 September 2026. Тверская left it for «Моя школа» on МЭШ the same day, Калужская in 2023 and
ЯНАО in 2025. A server a region has left can stay up: Тверская's `sgo.tvobr.ru` still answered
on 24 September 2026, version 5.56.4, with every sign-in enabled. So a live server is not
evidence that families still read it.

**Signing in has three shapes, and the region decides which.** The password flow — fetch a
salt from `/webapi/auth/getdata`, hash the password as `md5(salt + md5(password))` with the
password in **windows-1251**, post it to `/webapi/login`, carry the answer's `at` in a header
beside the `NSSESSIONID` cookie — is what every client implements, and it is switched off in
the regions that went ЕСИА-only. For those, netschoolpy (September 2026) drives ЕСИА itself,
including a QR login through the Госуслуги app; the official mobile app instead uses a device
code at `identity.ir-tech.ru`. Reports are generated asynchronously and delivered over a
SignalR hub, which is why a report route never returns the report.

**Where to start reading.** netschoolpy is the current, most complete client, but its GitHub
repository is gone and PyPI holds the only copy; nm17/netschoolapi is the classic reference
and is archived. Rows seen only in the minified bundles of a leaked 5.14 installation have exact
paths and unknown parameters.

**Signing in.**

*Password login (loginType=1) — the flow every open-source client uses; switched off in ESIA-only regions* — token carried as header `at` (numeric string ~26 digits, from the login response field `at`) + session cookie `NSSESSIONID` (and `ESRNSec` on asurso.ru / servers with the ESRN security module); alternative `Authorization: Bearer <accessToken>`. Lifetime: Session-bound: `timeOut` in the login response (900000 ms = 15 min in the 5.10 swagger example, 3600000 ms on asurso.ru); idle limit is the server setting `maxSessionIdleTime` (GET /webapi/settings/maxSessionIdleTime). netschoolpy keeps it alive with GET /webapi/context every 300 s. Validity can be asked with GET /webapi/context/expired?token=<at> (bool) and remaining life with UserContextController.GetLifetime.. Refresh: No refresh endpoint is used by any client: on HTTP 401 every client simply repeats the whole password login (nm17 `_request_with_optional_relogin`, netschoolpy `_authed_get`, netcitybot `sendRequest` also on 500). The login response carries `refreshToken` but nothing consumes it..

1. GET {origin}/webapi/logindata (no auth). Response sets the `NSSESSIONID` cookie and returns a JSON with login options: `schoolLogin` (bool, password login allowed), `esiaLogin`, `esiaMainAuth` (ESIA is the primary/only way in), `esiaButton`, `version` (server version string, e.g. "5.47.0"), plus windows/irtech/esa auth flags.
2. Resolve the school id: GET {origin}/webapi/schools/search?name=<part of name> → [{id, name, shortName, inn, ogrn, cityId, provinceId, addressString}] (the server requires at least one character; nm17 sends `name=У` to list everything). Older/other clients instead call GET /webapi/prepareloginform (→ {countries, cid, states, sid, provinces, pid, cities, cn, funcs, sft, schools, scid}) and GET /webapi/loginform?cid&sid&pid&cn&sft&LASTNAME=sft to walk country → state → province → city → school type → school. AdminAPI_SGO uses GET /webapi/addresses/schools?id=<scid> → [{id, name, countryId, stateId, municipalityDistrictId, cityId}] to fill cid/sid/pid/cn.
3. POST {origin}/webapi/auth/getdata (no body, cookie NSSESSIONID) → {lt, ver, salt} — all three are numeric strings; `salt` is one-shot.
4. Hash the password: `pw2 = md5(salt + md5(password encoded in windows-1251))` (hex, lower-case); `pw = pw2[:len(password)]`. Old servers sent the salt inside the login HTML (npanuhin regex 'salt') and the form went to /asp/postlogin.asp.
5. POST {origin}/webapi/login, Content-Type application/x-www-form-urlencoded, fields: loginType=1, scid=<school id> (optionally cid, sid, pid, cn, sft=2 as in the swagger `login_body`), un=<login>, pw=<pw>, pw2=<pw2>, lt=<lt>, ver=<ver>; optional rolegroup=<role id> when the first answer has `entryPoint` containing `choose-session-role` (accounts that are both staff and parent). Header `Referer: {origin}/` (asurso: `https://asurso.ru/about.html`), `X-Requested-With: XMLHttpRequest`. Response: {at, timeOut (ms, 900000 or 3600000), accessToken, refreshToken, tokenType:"Bearer", accountInfo:{user:{id,name}, userRoles:[{role:{id,name}, schoolId, userId}], organizations:[{id,name}], currentOrganization, loginTime, active, canLogin, storeTokens, accessToken, secureActiveToken}, entryPoint (e.g. "/asp/SecurityWarning.asp"), requestData:{warnType}, errorMessage, code}. Wrong credentials → HTTP 409 with {message}. Response also sets cookie `ESRNSec` (asurso.ru) which the SignalR endpoints require.
6. Store `at` and send it as header `at: <value>` on every later request (some clients also set `Authorization: Bearer <accessToken>`, which the swagger declares as `bearerAuth`, but `at` alone is what all clients rely on). Keep the cookie jar.
7. Bootstrap: GET /webapi/student/diary/init → {students:[{studentId, classId, iupGrade, nickName, className}], currentStudentId, weekStart, ...}; GET /webapi/years/current → {id,...} (or /webapi/mysettings/yearlist, or /webapi/context → schoolYearId); GET /webapi/grade/assignment/types?all=false → [{id, name, abbr}] to decode `typeId` in assignments; 4nk1r also GET /webapi/attachments/uploadLimits.
8. If `entryPoint` is /asp/SecurityWarning.asp the web UI posts `at`, `WarnType` to it; lentryd's request hook detects an HTML answer containing `/asp/SecurityWarning.asp` and POSTs ../asp/SecurityWarning.asp with {at, WarnType:2} then retries. Not needed for webapi-only clients.
9. Logout: POST /webapi/auth/logout (header at); servers < 5.29: POST /asp/logout.asp with form {at, ver}.

   `ver` from auth/getdata is also the page version that legacy ASP pages want as `VER`/`ver`; lentryd stores it in the Session. Login form field names are case-insensitive on the server (`UN`/`un`, `PW`/`pw`, `LoginType`/`loginType`). CURRENCY 2025–2026: a growing number of regions accept only Госуслуги (logindata.esiaMainAuth=true, schoolLogin=false): net-school.cap.ru and sgo.rso23.ru and sgo.prim-edu.ru show «Вход в систему 'Сетевой город. Образование' для всех пользователей возможен только с использованием учетных записей ЕСИА» (lentryd issue #26, 14 Dec 2025, for sgo.rso23.ru); netschool.edu22.info from 10 Jan 2026; Тульская область requires a verified ESIA account since 2015. Password login still works where schoolLogin is true (netschoolpy 8.0.2 docstring: sgo.e-mordovia.ru, version 5.47.0, «логин/пароль + Госуслуги»). Always read GET /webapi/logindata first and pick the flow from it.

*ЕСИА (Госуслуги) login with login/password, driven programmatically (netschoolpy ≥ 7, daniilok21 fork)* — token carried as header `at` + cookies of the SGO origin (NSSESSIONID and whatever the SSO callback set). Lifetime: same as password login. Refresh: none; netschoolpy cannot re-login automatically after an ESIA login (`_credentials` is cleared), it exports the session (`export_session` → JSON {access_token, student_id, year_id, school_id, cookies}) and re-imports it, validating with GET student/diary/init..

1. GET {origin}/webapi/logindata to obtain NSSESSIONID.
2. GET {origin}/webapi/sso/esia/crosslogin and follow the 30x chain (up to 20 hops, cookies collected by hand because they are set on several domains) until the URL is on esia.gosuslugi.ru (intermediate hop `esiasgo`). Browser User-Agent required (Chrome 120 UA string); TLS verification disabled and TLS1.3 switched off in netschoolpy because ESIA's chain breaks Python's defaults.
3. POST https://esia.gosuslugi.ru/aas/oauth2/api/login with JSON {login, password}; headers content-type: application/json, origin: https://esia.gosuslugi.ru, referer: https://esia.gosuslugi.ru/login/. Error → {failed: INVALID_PASSWORD\|INVALID_LOGIN\|ACCOUNT_LOCKED\|ACCOUNT_NOT_FOUND\|CAPTCHA_REQUIRED}. Success → {redirect_url} or {action: ENTER_MFA\|SOLVE_ANOMALY_REACTION\|MAX_QUIZ\|CHANGE_PASSWORD\|DONE, ...}; 200/201/202 all count as accepted.
4. ENTER_MFA: `mfa_details.type` is SMS, TTP/TOTP, MAX (code in the «Макс» messenger) or PUSH (Госключ). For a code: POST https://esia.gosuslugi.ru/aas/oauth2/api/login/otp/verify?code=NNNNNN (fallbacks tried on 404: /totp/verify, /mfa/verify, /otp-max/verify); `mfa_details.otp_details` carries phone, code_length, verify_timeout_secs, verify_attempts_left. For PUSH: POST /aas/oauth2/api/login/poll {challenge_id, state} every 3 s until {redirect_url}.
5. Post-MFA steps: GET /aas/oauth2/api/login/next-step; MAX_QUIZ → POST /aas/oauth2/api/login/quiz-max/skip {}; CHANGE_PASSWORD → POST /aas/oauth2/api/login/change-password/skip {}; SOLVE_ANOMALY_REACTION → POST /aas/oauth2/api/login/anomaly-reaction/start {guid} (sends SMS) then POST /aas/oauth2/api/login/anomaly-reaction/verify {code, guid}; loop until action DONE with redirect_url.
6. GET redirect_url and follow the callback chain (≤15 hops) back to {origin}; capture `loginState=<uuid>` from any URL or Location header on the way.
7. GET {origin}/webapi/logindata again, then GET {origin}/webapi/sso/esia/account-info?loginState=<uuid> → {users:[{id, roles:[{role:{id,name}}\|{id,name}], displayName\|name\|schoolName\|organizationName}]}. Empty `users` means the Госуслуги account is not linked to any SGO user.
8. POST {origin}/webapi/auth/login, Content-Type application/x-www-form-urlencoded; charset=UTF-8, fields: loginType=8, lscope=<user id from account-info>, idp=esia, loginState=<uuid>, optional rolegroup=<role id> → same JSON as the password login, take `at`. Copy the cookies of the SGO domain into the API client.
9. Bootstrap as in the password flow (student/diary/init, years/current, context → schoolId, grade/assignment/types).

   Web UI equivalents seen in the leaked login bundle: GET /webapi/sso/{idp}/info, GET /webapi/sso/trusted?loginState=, POST /webapi/sso/{idp}/users {loginState}, POST /webapi/sso/{idp}/get-auth-data-check {loginState}, GET /webapi/sso/{idp}/logout-url?idp&loginState, GET /webapi/sso/{idp}/logout?loginState, POST /webapi/auth/login-state (creates the loginState), GET /webapi/auth/mobile/info?loginState (says whether this login is for the mobile app), POST /webapi/auth/accounts {accounts:[...]} (validate remembered accounts), GET /webapi/auth/account (header at). `idp` values known: esia; the server enum IdentityProvider also covers the regional/‘esa’/‘irtech’/windows providers advertised by GET /webapi/settings/esiaAuth, /irtechAuth, /esaAuth, /windowsAuth. CURRENCY: this is the only programmatic way into ESIA-only regions and the flow netschoolpy 8.0.2 (Sept 2026) is built around; the ESIA private login API it drives is undocumented and changes without notice.

*ЕСИА login by QR code (Госуслуги app scans it) — netschoolpy `login_via_gosuslugi_qr`* — token carried as header `at` + SGO cookies. Lifetime: same as password login. Refresh: none (session export/import only).

1. Same crosslogin chain as above to land on esia.gosuslugi.ru and receive the `ESIA_SESSION` cookie.
2. POST https://esia.gosuslugi.ru/qr-delegate/qr/generate with JSON {esia_session:<cookie value>} (headers as in the ESIA API) → {signed_token, qr_id}. QR payload shown to the user: `gosuslugi://auth/signed_token=<signed_token>`.
3. Open a raw TLS socket and GET https://esia.gosuslugi.ru/qr-delegate/qr/subscribe/{qr_id} with `Accept: text/event-stream` and the ESIA cookies; ESIA sends no HTTP headers until the first event, so httpx/aiohttp streaming hangs — netschoolpy reads the socket by hand. Each `data:` line is JSON; an `error.code` of QR_AUTHORIZATION_SESSION_EXPIRED / QR_CODE_SESSION_NOT_FOUND / QR_CODE_SESSION_OUTDATED means retry (ESIA-007110 → regenerate up to 5 times with back-off); otherwise the event is the same login payload as step 3 of the password ESIA flow (redirect_url or action).
4. Continue with MFA handling, callback chain → loginState, account-info, POST /webapi/auth/login (loginType=8, idp=esia, lscope, loginState, rolegroup).

*Session reuse from a browser (netschoolpy `login_with_cookies`, `login_with_token`, `login_with_session_store`)* — token carried as header `at` and/or cookie `NSSESSIONID`. Lifetime: until the browser session expires on the server. Refresh: none.

1. Either paste the `NSSESSIONID` cookie (32 hex chars) / full Cookie string, or the `accessToken` taken from the SPA's localStorage `session-store` (JSON with `accessToken`/`at`, or a list of accounts with `active`).
2. Set header `at` (from token) or only the cookie; GET /webapi/student/diary/init — if it works the session is alive; the response header `at` (if present) is adopted.
3. GET /webapi/years/current, GET /webapi/context (schoolId, organizationName, dateFormat), GET /webapi/grade/assignment/types.

*Mobile app login (device-code via IRTech identity server) — mezhendosina/che-zadali-app* — token carried as header `Authorization: Bearer <access_token>` (JWT from identity.ir-tech.ru). Lifetime: `expires_in` seconds from the token response (the app stores now+expires_in and refreshes when past). Refresh: POST https://identity.ir-tech.ru/connect/token grant_type=refresh_token.

1. Open a WebView at {region-origin}/authorize/login?mobile (the user logs in there with password or Госуслуги).
2. On success the page redirects to a custom scheme `irtech://...?pincode=<int>`; the app captures `pincode` (the web side calls GET /webapi/mysettings/mobile/pincode and POST /webapi/mysettings/mobile/set-link).
3. POST https://identity.ir-tech.ru/connect/token, application/x-www-form-urlencoded: grant_type=urn:ietf:params:oauth:grant-type:device_code, device_code=<pincode>, client_id=parent-mobile, client_secret=<redacted> → {access_token, expires_in, id_token, refresh_token, scope, token_type}.
4. All `api/mobile/*` calls on the region origin (and GET https://identity.ir-tech.ru/users?v=2) carry `authorization: Bearer <access_token>`.
5. Before expiry: POST /connect/token with grant_type=refresh_token, refresh_token=<...>, same client_id/secret.

   The leaked 5.14 install has a separate `MobileGate` site (IRTech.NetCity.Edu.Mobile.ClientService, Swashbuckle, HostUrl https://10.11.4.25:44335/, Authority https://auth.ir-tech.ru/core) — the older mobile back end; its routes are not visible in the leak (compiled DLLs only). The web login page also has `?mobile`, `access_token` and `idpBindUser` query handling and GET /webapi/users/get-mobile. CURRENCY: unverified since May 2024 (single source, che-zadali-app); treat as uncertain.

*Legacy HTML login (servers ≤ 4.x / 2021, npanuhin/NetSchool-parser)* — token carried as form fields AT and VER on every POST (no header). Lifetime: server session. Refresh: none.

1. GET {origin}/ and read hidden inputs VER, LoginType, LT and the salt (regex in the page).
2. POST {origin}/asp/postlogin.asp with CID, PID, CN, SFT, SCID, PCLID, PCLID_IUP, SID, UN, PW2=md5(salt+md5(password cp1251)), PW=PW2[:len], VER, LoginType, LT.
3. If the answer is /asp/error.asp → wrong password. If it contains a form to /asp/SecurityWarning.asp → POST it with ATLIST, AT, VER, WarnType=1.
4. Read `AT` and `VER` hidden inputs from every page; POST them to every /asp page; logout with POST /asp/logout.asp {AT, VER}.

*OpenID Connect / OAuth2 provider built into SGO (server side only, for third parties)* — token carried as Authorization: Bearer (JWT issued by the SGO instance). Lifetime: unknown. Refresh: unknown.

1. **Headers the clients send.**

| Header | Value | Why |
| --- | --- | --- |
| `at` | <at from POST /webapi/login> | The session token every /webapi call is authorised with; missing/expired → 401. Set on the httpx/OkHttp client after login (nm17, netschoolpy, 4nk1r, netcitybot, asurso). |
| `Cookie` | NSSESSIONID=<hex32>; ESRNSec=<value on asurso.ru> | NSSESSIONID is created by GET /webapi/logindata or POST /webapi/auth/getdata and must accompany POST /webapi/login (the salt is tied to it). ESRNSec (asurso.ru) is set by the login response and is mandatory for /WebApi/signalr/* — without it the WebSocket upgrade is answered 403. |
| `Referer` | <region origin>/ (asurso: https://asurso.ru/about.html; lentryd on get-attachments: <origin>/angular/school/studentdiary/) | Every client sets it; nm17 and netschoolpy put it on the client by default. The server checks it on some legacy pages and on login. |
| `X-Requested-With` | XMLHttpRequest | Set by netcitybot and 4nk1r on all calls and by asurso on the POST /webapi/login only; the ASP.NET side treats the request as AJAX and returns JSON/401 instead of HTML redirects. |
| `Accept` | application/json, text/javascript, */*; q=0.01 | netcitybot/4nk1r/AdminAPI_SGO copy the browser's AJAX Accept header; text/event-stream for the SignalR SSE transport. |
| `User-Agent` | any; clients use NetSchoolAPI/5.0.3, NetSchoolPy/1.0, sgo_api, or a Chrome UA | SGO itself does not check it; ESIA does — netschoolpy uses a desktop Chrome UA for the Госуслуги chain. |
| `Content-Type` | application/x-www-form-urlencoded (login, auth/login, all /asp pages) or application/json (get-attachments, reports/*/queue, mail/*, users/staff/registry) | POST /webapi/login is form-encoded; JSON endpoints reject forms. |
| `Authorization` | Bearer <accessToken> (webapi, optional) / Bearer <identity.ir-tech.ru access_token> (api/mobile, required) | The swagger declares bearerAuth and netcitybot sets it from `accessToken`, but for /webapi the `at` header is what actually authorises; for /api/mobile it is the only credential. |

**Captcha and second factor.** SGO itself has no captcha on /webapi/login (clients see 409 on a wrong password). Госуслуги: CAPTCHA_REQUIRED after too many attempts (not solvable by netschoolpy), MFA by SMS / TOTP / «Макс» code / Госключ push, plus «security check» (SOLVE_ANOMALY_REACTION → SMS) and MAX_QUIZ interstitials which netschoolpy skips. The login page also supports a pin-code hand-off to the mobile app. In ESIA-only regions ЕСИА MFA is therefore unavoidable for an unattended client: netschoolpy exports/imports the session (cookies + at) instead of re-logging in.

Role choice: a user who is both staff and parent gets `entryPoint` "…choose-session-role…" and must repeat the login with `rolegroup=<role id>` (netschoolpy auto-picks the role whose name contains «Родитель»). Parent accounts with several children: switch with POST /webapi/context/session?key=State47 (body: the bare student id; GET with the same key reads it back) or just pass another `studentId` from student/diary/init to the diary calls. Datacenter IPs: sgo.volganet.ru refuses them; netschoolpy retries through Tor (socks5://127.0.0.1:9050) or a user proxy on ConnectError/ConnectTimeout, retries 5xx three times, and loops on ReadTimeout. Currency (Sept 2026): the password flow is being retired region by region in favour of ЕСИА; the pin-code/mobile flow is unconfirmed since 2024; no mos.ru-style ID or app-only token has replaced the `at` session token — every 2026 client still authorises /webapi with header `at` + NSSESSIONID.

**Formats.**

- *Dates*: JSON dates are naive local ISO without zone: `2023-04-10T00:00:00` (day, date, dueDate, weekStart, postDate, loginTime with fraction `2022-01-13T22:37:38.7883797`); lesson times are `"08:30"` strings. Query params weekStart/weekEnd/startDate/endDate take `YYYY-MM-DD`. Report `period` filterValue is `"<start ISO> - <end ISO>"` (lentryd date2JSON `YYYY-MM-DDT00:00:00`, mytypy `2024-09-01T00:00:00.000Z - 2024-11-04T00:00:00.000Z`); report params DATEFORMAT is the server's `context.dateFormat` (e.g. `d\u0001mm\u0001yyyy\u0001.`) and SERVERTIMEZONE an int (3). Legacy ASP pages take `dd.mm.yy` (Calendar `date`, GetMessagesAjax returns `dd.MM.yyyy hh:mm`); report HTML shows `dd.mm.yy`/`dd.mm.yyyy`. netschoolpy's assignment schema uses `%Y-%m-%dT00:00:00`.
- *Ids*: All entity ids are integers (studentId, classId, yearId, assignmentId, classmeetingId, attachmentId, userId, schoolId, subject/term ids); `at` is a numeric string of ~23–26 digits; lt/ver/salt are numeric strings; loginState is a UUID; SignalR ConnectionToken is an opaque base64-ish string; report file ids (`files/{id}`) are opaque strings; region address ids cid/sid/pid/cn/sft/scid are small ints (cid=2 Russia, pid=-1 none, sft=2 school); class filter value for reports is `"<classId>_0"` (PCLID_IUP); the identity server issues JWTs.
- *Pagination*: Diary/pastMandatory are range queries by week (any range inside the school year); announcements use `take` (-1 = all) with no offset; new mail uses `page` (1-based) + `pageSize` in the POST /webapi/mail/registry body with `order:{fieldId,ascending}`; legacy GetMessagesAjax.asp uses jTable `jtStartIndex`/`jtPageSize`/`jtSorting` ("Sent DESC"); forum pages use PAGE/PAGESIZE; users/staff/registry takes `page`/`pageSize` (null = all); api/mobile has no pagination (date ranges).
- *Notes*: Marks: `mark.mark` int (or null), `dutyMark` bool («точка»/долг), `resultScore`, `weight` int on assignments (weighted average only when diary/init.weight is true, maxMark 5), `typeId` decoded through grade/assignment/types (3 = «Домашнее задание» in the che-zadali sample); special non-numeric marks in reports (netschoolpy SPECIAL_MARK_DESCRIPTIONS). Text answers appear as `textAnswer{answer, answerDate}` inside the diary assignment. Strings are UTF-8 JSON; legacy ASP pages are windows-1251 HTML.

**Caveats.**

- The route table is a union across server versions 4.x (2021) → 5.10 (2022 swagger) → 5.14 (leaked install) → 5.24/5.29/5.32 feature gates (lentryd, 2025) → whatever the regions run in 2026 (netschoolpy reads `version` from GET /webapi/logindata). Routes marked legacy (/asp/*.asp, /WebApi/signalr/*, /webapi/queueHub) still exist on older regional servers but the current SPA uses the webapi + /webapi/signalr/queueHub equivalents.
- Rows sourced only from CryEvs/NetCity come from the minified Angular bundles of a leaked 5.14 installation: method and path are exact, but parameters and response shapes were not read for most of them (897 method+path pairs were extracted; the table lists the student/parent/auth-relevant ~60 plus a sample of staff ones). The remaining routes (users/userinfo/classes/subjectgroups/curriculum/movement/em/parentpay/talents/…) are staff/admin-only. WebApi controllers are compiled DLLs, so server-side route attributes could not be verified; the XML doc comments were used only for purpose text.
- The official swagger (kmlebedev/netSchoolWebApi, «The API for the NetSchool irTech project») was generated by a third party from captured traffic, not published by ИРТех; it is nevertheless the only machine-readable description and matches all clients.
- Password hashing detail: every client hashes the password as windows-1251 bytes (`md5(password.encode('windows-1251'))`), then `md5(salt + hex)`; a UTF-8 hash fails for passwords with Cyrillic letters. `pw` is `pw2` truncated to the password length.
- The ESIA (Госуслуги) endpoints are those of esia.gosuslugi.ru's private login API as reverse-engineered by netschoolpy in 2026; they change without notice, the QR SSE needs a raw socket, MFA action names (ENTER_MFA, MAX_QUIZ, SOLVE_ANOMALY_REACTION, CHANGE_PASSWORD, DONE) are as observed, and CAPTCHA_REQUIRED cannot be passed programmatically. On regions where `esiaMainAuth` is true (Госуслуги is the only entrance) password login is refused.
- The mobile API (`/api/mobile/*`, identity.ir-tech.ru `connect/token` with client_id `parent-mobile` and a hard-coded client_secret) is seen in exactly one client (che-zadali-app, May 2024, built for sgo.edu-74.ru). The secret is the app's, may have rotated, and the WebView pincode step depends on the region's login page supporting `?mobile`.
- `student/diary/init` is inconsistent across versions: `students` is a list on new servers and a dict keyed by index on some, and `currentStudentId` is an index there (netschoolpy `_init_students` handles both). `student/diary/get-attachments` may return `attachmentGuid` instead of `id` (freeuser3 fork).
- Report generation is inherently asynchronous: POST reports/{id}/queue returns taskId (+queueKey), the file id arrives only over SignalR; on asurso.ru the WebSocket is 403 without the ESRNSec cookie, and on new servers the web client first calls GET /webapi/earlyaccess?accessKey=irtechsignalr. Report content is HTML tables (or PDF with ?output=Pdf) that must be parsed; DATEFORMAT in the params must be the server's own (`context.dateFormat`, e.g. "d\x01mm\x01yyyy\x01.").
- Some regional servers refuse datacenter IPs (sgo.volganet.ru) or are reachable only on odd ports (edu.admoblkaluga.ru:444, netcity.admsakhalin.ru:11111); netschoolpy falls back to Tor or a user proxy. Several regions (Свердловская, Иркутская, Ростовская области, Санкт-Петербург's private ФТШ instance) run more than one independent NetSchool server, so a region → host map is incomplete by nature; the Petersburg public diary (dnevnik2.petersburgedu.ru) is a different platform and is out of scope here.
- No live endpoint was probed (network to the diary hosts is blocked); everything above is from source code, package archives, the gitbook doc and the leaked front-end.
- spo.asurso.ru (Alekzum/ASURSO-API, PyPI asurso-api) is the college (СПО) product with a different API under /services/* (security/login, students/{id}/dashboard\|attestation, reports/current/performance/{id}, people/organization, integration/chatManagement/chats/current); it is not the NetSchool webapi and its routes are deliberately not in this table.
- The CryEvs 5.14 bundles contain about 900 distinct method+path pairs (all $http calls); this table carries the student/parent/auth-facing ones and a sample of staff ones. Most staff/admin routes (userinfo, staff, subjectgroups CRUD, curriculum, movement, em/*, settings/* setters) are left out on purpose.
- CURRENCY (Sept 2026): the platform is shrinking. Чувашия, Краснодарский край, Свердловская and Челябинская области moved schools to the federal ТОР «Моя школа» / «Госуслуги Моя школа» for 2026/27; their SGO hosts may stay up (archive, colleges, staff) but should not be assumed to hold current diaries. «Моя школа» is a different platform and its API is out of scope here.
- CURRENCY: the password flow (POST /webapi/login, loginType=1) is refused in ESIA-only regions (Краснодарский, Чувашия, Приморский, Алтайский край from 10 Jan 2026, Тульская since 2015); read GET /webapi/logindata (schoolLogin / esiaMainAuth) before choosing a flow.
- CURRENCY: of the open-source clients, nm17/netschoolapi (last commit Sept 2024) and lentryd/NetSchoolApi (archived May 2026) are frozen and the netschoolpy GitHub repository is gone (PyPI 8.0.2 remains). The 2026 evidence rests on netschoolpy 8.0.2, freeuser3/netschool-api-plus 11.1.0 and cfmz/asurso-bot.
- ИРТех publishes no public API documentation; the swagger used here is third-party (5.10, 2022). Nothing was added from official documentation.
