# «Электронная школа 2.0» — Кузбасс

*Part of [the electronic diaries of Russia’s regions](../diaries.md). Verification: extracted, checked against the code, and dated. Confidence of the whole: medium. Nothing here has been tried against the live service.*

**The regional system of Кемеровская область — Кузбасс**, by ООО «МИРИТ», with the pupil and
parent app «#УЧУСЬВКУЗБАССЕ». Its mobile API at `api3d.ruobr.ru` is the only diary API in the
country that takes the credentials in headers on every request: `username` is the upper-cased
login in base64, `password` the password in base64. There is no token and no session to lose.

**What that rests on.** One author reverse-engineered the app in 2022 (`ruobr_api` 2.0.2, sixteen
methods), and nothing has been added since; the app surely calls more. The best evidence that
it still works is a bot that runs that 2022 library unchanged in September 2026. The older
`ruobr.ru/api/` answers 403 since April 2022 and is legacy.

**The web cabinet is a different matter.** `cabinet.ruobr.ru` has signed families in through
Госуслуги only since 1 July 2024, and no client drives that; the form login its old clients used
is legacy. Whether the mobile API's header credentials still work for an account created
through Госуслуги is not known.

**Signing in.**

*Mobile API: credentials in headers on every request (api3d.ruobr.ru, and identically ruobr.ru/api/)* — token carried as header: `username` (base64 of upper-cased login) and header: `password` (base64 of password), sent on every request. Lifetime: No token; credentials are replayed on every call. Clients store the login/password (the unified bot encrypts them with Fernet, the VK bot stores them in Postgres).. Refresh: None — there is nothing to refresh..

1. Take the login, convert it to UPPER CASE, UTF-8 encode and base64 it: username = base64(login.upper()).
2. Take the password unchanged, UTF-8 encode and base64 it: password = base64(password).
3. Send BOTH values as HTTP request headers named exactly `username` and `password` on EVERY request; there is no login endpoint, no session and no token. (This is not HTTP Basic auth: two separate custom header names.)
4. The first call the clients make is GET https://api3d.ruobr.ru/user/ — it doubles as the credential check. A pupil account answers with its own profile (status == 'child'); a parent account answers status == 'applicant' with the children in `childs[]`.
5. Choose a child: every child-scoped route takes `?child=<id>` where <id> is the `id` field of the selected child (or of the pupil profile itself). The clients keep an index into `childs` and pass childs[index].id.
6. Failure detection: an empty/false JSON body from user/ means wrong credentials (ruobr_api raises AuthenticationException); otherwise a dict with `success: false` carries either `error` (message) or `error_type` ('auth' == bad credentials; the 2.x author comments «не уверен, что это всё ещё работает» about error_type). A non-JSON body (HTML, 502) is raised as NoSuccessException with the raw text.

   ruobr_api itself sets no User-Agent, Accept, device id or app-version header, but the only live client (ruobr-unified-bot, main.py) patches httpx's default User-Agent to a desktop Chrome/120 string because QRATOR (DDoS protection of ruobr.ru) answers 403 Forbidden to 'python-httpx/x.y.z'; send a browser-like User-Agent. Mail detail (mail/{id}/) is documented to fail with 502 Bad Gateway when the message's type_id == 2 (HTML message). Currency: this header scheme with a local login/password is still accepted in 2026 per ruobr-unified-bot (commit 2026-09-12), even though the web cabinet became ЕСИА-only on 01.07.2024 and the RuStore listing of the old app says it signs in through Госуслуги — so accounts created through Госуслуги may have no login/password usable here; how the app turns an ЕСИА sign-in into credentials for api3d is not in any open client.

*LEGACY — Web cabinet: Django form login on cabinet.ruobr.ru (AnyBalance provider, ruobr-student); removed for parents/pupils on 01.07.2024* — token carried as cookie: `sessionid` (Django session) with `csrftoken` beside it, both set by the GET+POST of /login/; names seen in ruobr-student cookie.py (self.csrftoken, self.sessionid = cookies.values()). Lifetime: Not visible in the code.. Refresh: Re-login..

1. GET https://cabinet.ruobr.ru/login/ (ruobr-student; the AnyBalance provider writes /login without the slash) with a browser-like User-Agent and Accept: text/html…; the response sets the Django `csrftoken` cookie and carries an HTML form. ruobr-student fails with RequestError on any status other than 200.
2. POST the same URL as application/x-www-form-urlencoded with `username` and `password` (plain, not base64) plus `csrfmiddlewaretoken`. ruobr-student takes csrfmiddlewaretoken from the value of the `csrftoken` cookie; AnyBalance instead copies every hidden input of the form. Referer: https://cabinet.ruobr.ru/ (ruobr-student) or https://cabinet.ruobr.ru/login (AnyBalance).
3. Success: the session cookie jar then holds exactly two cookies, `csrftoken` and `sessionid` (ruobr-student raises AuthorizationError when fewer than two are present); AnyBalance checks for the word «logout» in the returned HTML. Failure: <div class="form_errors"><p>…</p> in the HTML (AnyBalance matches /пользовател\|парол/ to classify it as a credential error).
4. Every later cabinet request sends the `csrftoken` and `sessionid` cookies (ruobr-student passes the dict to requests/aiohttp as cookies=) together with the browser-like headers. The landing HTML after login already contains the «Питание» section («№ Лицевого счёта», «Cостояние счёта», «Субсидия», «Комплекс по умолчанию») that AnyBalance scrapes; the /student/ pages (schedule JSON, progress HTML) are what ruobr-student reads.

   Verified 2026-09-24 by WebFetch of https://cabinet.ruobr.ru/login/: the page has no username/password form any more — only «Войти через гос услуги» (→ /esia/v3/auth/) and the notice «С 01.07.2024 вход только через подтвержденную учетную запись Госуслуг». The steps above describe the pre-July-2024 form (ruobr-student 2023-10-28, AnyBalance 2013). No client implements the ЕСИА chain.

*Web cabinet (current): Госуслуги / ЕСИА sign-in on cabinet.ruobr.ru* — token carried as cookie (presumably Django `sessionid`; not verified). Lifetime: Not visible.. Refresh: Repeat the ЕСИА sign-in..

1. GET https://cabinet.ruobr.ru/login/ — the page offers only «Войти через гос услуги».
2. Follow the button to https://cabinet.ruobr.ru/esia/v3/auth/, which starts the ЕСИА (Госуслуги) OAuth redirect chain.
3. Sign in on Госуслуги with a verified (подтверждённая) account whose ФИО, date of birth, СНИЛС and passport are filled; a pupil's own account must be linked to a parent's and consented to.
4. ЕСИА redirects back to cabinet.ruobr.ru; the callback path and the session cookie are not visible in any source (the pre-2024 cabinet used Django `sessionid`).

   Source: live page https://cabinet.ruobr.ru/login/ (WebFetch 2026-09-24). Automating it needs a Госуслуги login, possibly with SMS/2FA on the ЕСИА side; no open client does it.

*Staff web sign-in on ruobr.ru («Вход для сотрудников»)* — token carried as cookie (not visible).

1. GET https://ruobr.ru/accounts/login/ (same page at https://ruobr.ru/): choose «Сотрудник ОУ» or «Оператор».
2. Either use the page's own form (field names not visible) or «Войти через гос услуги» → https://ruobr.ru/esia/auth/.

   Staff only; not used by any client. The teacher mobile app (com.mirit42.mjk) is described on RuStore (v28.0.0, 2025-02-15) as signing in only through the MAX messenger — nothing more is known about that flow.

**Captcha and second factor.** None on the mobile API in any client. The parent/pupil web cabinet is ЕСИА-only since 01.07.2024 (verified on the live /login/ page 2026-09-24), which brings Госуслуги's own sign-in (and its SMS/2FA if the account has it) in front of the cabinet; no open client implements that chain. The teacher app reportedly signs in only through MAX.

Rate limiting: none observed or handled by name. The VK bot retries every request forever on httpx ConnectTimeout («timeout, trying again»); the unified bot wraps every call in a 30 s timeout with 3 attempts and exponential backoff (1 s, 2 s, 4 s), retries on success:false and network errors, never on auth errors, and caches the children list for 24 h to avoid re-hitting user/. The unified bot also patches httpx._client so that requests to api3d.ruobr.ru can go through a SOCKS5 proxy (BOT_PROXY) — it runs from outside Russia. QRATOR (DDoS protection in front of ruobr.ru, including api3d) rejects the python-httpx default User-Agent with 403 per ruobr-unified-bot main.py. Currency (2026): the api3d header scheme is the only credential path any open client uses and it still works per ruobr-unified-bot; the web-cabinet form login is gone (ЕСИА only).

**Formats.**

- *Dates*: Query dates are 'YYYY-MM-DD' (start, end, selected_date, date). Times in lessons are 'HH:MM:SS' ('08:30:00'). Response datetimes (mail post_date, news pub_date) are ISO-like 'YYYY-MM-DD HH:MM:SS' parsed with datetime.fromisoformat; task.deadline is 'YYYY-MM-DD' (the VK bot parses it with fromisoformat and prints the time when present). The unified bot added a normaliser because meal-visit `date` was observed in non-ISO forms (DD.MM.YYYY etc.). Client-side 'today' is computed in Asia/Novokuznetsk (VK bot) or Asia/Krasnoyarsk (Telegram bot) — both UTC+7.
- *Ids*: Integer ids everywhere: child/pupil `id` (7 digits, e.g. 4694228) distinct from `user_id` (9 digits); lesson `id`, task `id`, message `id`, `subject_id`, `question_id`, `staff_id`, `school_id`. Legacy food history has complex__uid as a UUID. Period is a small integer (1–4) with a Roman numeral twin `rom`.
- *Pagination*: None. Every list is returned whole; the diary is bounded only by start/end.
- *Notes*: Envelope conventions: most 2.x routes wrap the payload in `data`; /timetable2/ uses `lessons`, /mail/ uses `messages`, /controlmark/ returns a bare list, /btm/ and /user/ return the object itself. Errors come as {success:false, error\|error_type} with HTTP 200, or as non-JSON (502 on HTML mail). Money is a string in /food/calendary/ (balance, price_sum, comma possible) but integer kopecks in the legacy /food/. Booleans are sometimes ints (readonly, school_is_tourniquet, done, ordered as '1'/'True').

**Caveats.**

- Everything here is reverse-engineered from the mobile app by one author (raitonoberu); there is no official or documented API. The 2.x route list is exactly the 16 methods of ruobr_api 2.0.2 — the app almost certainly calls more (push settings, GPS tracker, tourniquet, message sending) and none of that is in the open.
- ruobr_api has had no commit since April 2022 and no PyPI release since; the VK bot stopped in November 2023. Only ruobr-unified-bot (September 2026) is live, and it still runs the 2022 library unchanged, which is the best available evidence that api3d.ruobr.ru and the username/password headers still work — but it is second-hand and no route was probed from here.
- /homework/detail/ and /journal/homework/detail/ on api3d.ruobr.ru, and the media download with credential headers, are guesses the unified bot tries and silently drops; they are recorded as uncertain and nothing shows any of them answering.
- The legacy ruobr.ru/api/ routes are known only from the 1.x wheels; the switch to api3d in 2.0.0 suggests they were retired, but nobody recorded whether they still answer. Response shapes there (marks as a dict, task as a single object) differ from 2.x.
- Response field lists are the union of what the clients read, not a schema: the unified bot hedges on alternate key names (list/do_list/programs, sum/program_sum, file/url/link) which shows the author was not certain of the exact keys either. /btm/, /book/, /birthday/, /ios/, /all_marks/, /mail/{id}/ and /mail/new/ have no documented shape at all.
- ruobr-unified-bot's README calls the system «Руобр (Новосибирская область)»; every other source, the vendor pages and the govdomains list place it in Кемеровская область — Кузбасс. The platform is single-region; there are no other instances to enumerate.
- FLOERKA/ruobr-api-java contains no code (README only) and adds nothing beyond confirming the /user/ shape.
- QRATOR (DDoS protection of ruobr.ru) is reported by ruobr-unified-bot to reject httpx's default User-Agent with 403; ruobr_api 2.0.2 itself sends that default, so the library used unpatched may now fail before authentication is even checked.
- The cabinet's /student/ section (ruobr-student) is for students of vocational colleges («для студентов»); whether school pupils/parents have equivalent JSON endpoints in the cabinet is not shown by any client. Only two /student/ routes are known, and the 'g0' segment of get_schedule is unexplained.
- The web cabinet's form login is gone: the live /login/ page (2026-09-24) offers only Госуслуги (/esia/v3/auth/) since 01.07.2024. The AnyBalance and ruobr-student logins are therefore legacy, and the /student/ routes can only be reached (if at all) after an ЕСИА sign-in no open client performs.
- The mobile API with local login/password in headers still works in September 2026 per ruobr-unified-bot, but the parent app was relaunched (com.mirit.uchusvkuzbasse_new, v42.0.0, 2026-09-17) with features (event feed, praise, canteen contract signing) that no open client covers. Whether the relaunched app still uses api3d.ruobr.ru and these 2022-era paths, and how an ЕСИА-only account obtains api3d credentials, is not established. Expect breaking changes of the April-2022 kind (ruobr_api issue #3: the old API was switched off to 403 when the old app was retired).
- Every https://ruobr.ru/api/ route is dead (nginx 403 since April 2022, ruobr_api issue #3); they are kept only as history.
- No evidence either way on Кузбасс joining ФГИС «Моя школа» / ТОР in 2026: web search was unavailable in this pass (budget exhausted, DuckDuckGo captcha, Bing irrelevant). Nothing on the vendor pages mentions it; the vendor relaunched its own app in September 2026, which suggests the regional system continues.
- The teacher app (com.mirit42.mjk) reportedly signs in only through the MAX messenger (RuStore description, 2025); nothing else is known about the teacher API.
