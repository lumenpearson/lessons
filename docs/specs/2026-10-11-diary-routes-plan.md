**Status:** drafted on 11 October 2026 against `3fc7f54` (read-only; nothing run, counts added by hand), and committed as the first commit of `server/diary-routes`, cut from `main` at `a28473e`. The run at each task's gate is the truth.

**Goal:** Make `DIARY_EGRESS = direct | proxy | relay` the deployment's choice of how it reaches the diaries.
- Under `proxy`, Petersburg and the twelve «Сетевой город» regions that answered from the RUVDS proxy on 11 October go through `DIARY_PROXY_URL`. The other seven stay direct until the relay (#408).
- v2's `GetDiaryCapabilities` reports the route.
- The tick's self-check probes every «Сетевой город» region in use by its own route.

**Architecture:**
- **The setting** (`app/config.py`).
  - `Settings.diary_egress` holds the raw value.
  - `diary_egress_asked` is one of the three words, or `None`.
  - `diary_egress_value` is the egress as it takes effect: `DIRECT` or `PROXY`, never `RELAY`.
  - `DiaryEgress` is a `StrEnum` named like the proto's values.
  - The setting is optional and never in `deployment_problems`. The startup log announces only what does not take effect as written, and never repeats an unusable value.
- **The route table.**
  - `Region.via_proxy` in `providers/netschool/regions.py`: twelve rows are true, as the owner's probe found.
  - `Row.via_proxy` in `providers/diary/registry.py`: true for Petersburg, a one-server provider.
  - `Row.proxied(region)`, `registry.route(key, region, settings)` and `registry.proxy_for(...)` together are the one answer to «how does this deployment reach this server».
- **Two pools, chosen per call.**
  - `NetSchoolClient` holds its region and fetches its pool on every call, inside `_send` and `terms_search`.
  - `client_for(region)` hands it `proxied_client()` or `shared_client()`.
  - `shared_client()` keeps its meaning, the direct pool, so every existing test fake still holds.
  - Petersburg's one pool is built with `proxy_for(PETERSBURG)`.
- **The contract.** Additive and v2 only: the enum `DiaryEgress`, the message `DiaryRoute`, `DiaryCapabilities.egress = 3` and `ProviderCapabilities.routes = 5`.
- **The self-check.**
  - One `health_checks` row per «Сетевой город» region in use, `diary_region:<key>`, probed with `GET /webapi/logindata` by the region's route.
  - The four fixed checks keep their names. `diary_proxy` reads unknown when the egress sends nothing through the proxy.
  - Rows of regions no longer in use are deleted.
  - Proxied regions read unknown while the proxy itself is down.
  - A «down» alert carries a one-line hint by route.

**Tech Stack:** Python 3.12, httpx (`proxy=` per client), pydantic-settings, SQLAlchemy 2.1 async, protobuf-py and connectrpc generated by Buf 1.73.0 from remote plugins, pytest with `httpx.MockTransport`.

**Spec:**

- The owner's decisions of 11 October 2026: routing by region, the alert's hint, and the privacy policy naming the proxy.

## Rulings for #406

1. **`DIARY_EGRESS` is optional and never refuses a deployment.**
   - Unset or unusable, it reads as `proxy` where `DIARY_PROXY_URL` is usable and `direct` otherwise, which is exactly what production has today.
   - Case and spacing are ignored.
2. **`relay` is accepted, announced as not built (#408), and behaves as `direct`.**
   - A deployment that asks for the relay chose not to depend on a proxy. Falling back to one it may still carry would send its families' calls through a hop it declined.
   - The capabilities say `DIRECT`, so no phone relays to a server that has nowhere to relay to.
3. **`proxy` without a usable URL is `direct`.** This is announced only when the URL is empty; an unusable URL already has its own line.
4. **`direct` beside a usable URL is a choice and announces nothing.** `diary_proxy` reads unknown: «DIARY_EGRESS is direct: no diary goes through the proxy».
5. **The route is a static table.**
   - `Region.via_proxy` is true for the twelve hosts that answered the school search through RUVDS on 11 October, and `Row.via_proxy` is true for Petersburg.
   - Nothing tries one route and then the other: the owner rejected a dynamic fallback.
   - Altai Krai (ЕСИА-only, never called) is marked as the probe found it.
6. **The route lives in the registry.** It is the diary-as-data answer, and `rpc/` may already import the registry. No new module is added, so mypy stays at 240.
7. **«Сетевой город» gets a second pool beside the first, chosen per call by `client_for(region)`.**
   - `shared_client()` keeps its name, its signature and its meaning: the direct pool.
   - `terms_search` goes through `client_for` as `_send` does.
   - `close_client()` closes both pools.
8. **The capabilities report the egress as it takes effect, in two additive v2 fields.**
   - `DiaryCapabilities.egress` is the deployment's egress.
   - `ProviderCapabilities.routes` holds one `DiaryRoute`. For a one-server provider it has no region; for a regional one there is one per listed region, in `regions`' order.
   - Under `proxy`, five password regions stay direct, so a single value would make the phone guess.
9. **v1's `/diary/capabilities` keeps its shape.** Nothing that reads v1 will act on a route; the relay ships with the move to v2. `test_contract_mirror.py` records the addition.
10. **The self-check probes each «Сетевой город» region in use, by its route, as a row of its own.**
    - «In use» means bound by `classes.diary_region`, or the region of a live (unexpired) «Сетевой город» session, filtered through `Row.served_region`.
    - The probe is `GET /webapi/logindata`, sent with the diary client's headers and user agent.
    - Any answer but a refusal is `ok`. No answer, a 403 or a WAF page (`looks_refused`) is `failing`.
    - The row's name is `diary_region:<key>`, at most 24 characters in a column of 32, so no migration.
11. **While the proxy is down, the proxied regions read unknown.** The owner hears one alert for the proxy, not thirteen.
12. **A tick probes at most 17 diary servers:** Petersburg through the proxy, plus the 16 regions that take a password. They all run at once inside the checks' existing budget.
13. **Rows of regions no longer in use are deleted.** If the query for regions in use fails, the region rows are left alone.
14. **The suite pins `DIARY_PROXY_URL` and `DIARY_EGRESS` empty (#419),** and conftest answers every region probe with a fake.
15. **A region's «down» alert says what to do, by the route the failing probe took.** This is the owner's decision of 11 October 2026.
    - Through the proxy: «Регион мог закрыть доступ с адреса прокси — переведите его на прямой маршрут (via_proxy в regions.py).»
    - Directly: «Регион мог закрыть доступ с адреса сервера — проверьте его через прокси и, если отвечает, включите via_proxy в regions.py.»
    - The line goes after the first and before the reason, which stays last.
    - It rides on `Result.hint`, set from the route, never from the reason's wording, and it is never written to `health_checks`.
    - «up» carries no hint; «reminder» carries it.
16. **The privacy policy names the proxy.** This is the owner's decision of 11 October 2026.
    - «Третьи стороны», and its twin «Third parties», each gain one point at the same place: the operator's intermediary server in Russia, at RUVDS.
    - The point says: an HTTP proxy and a TLS tunnel, which sees the diary site's address and the time and may log them, and never sees logins, passwords, sessions or marks.
    - `legal.json`'s edition goes from 2 to 3.

## Risks, and what cannot be verified without production

- **The twelve were seen to answer a school search, not a sign-in or a read.** Whether every path passes through Squid unchanged is unverified.
- **The five direct password regions' reachability from Vercel's `fra1` is unknown,** as it was before. The new checks will say so.
- **Concentration on one address.** Eleven served regions and Petersburg share the RUVDS IP, so the proxy is a single point of failure for them.
- **No setting undoes only the «Сетевой город» half.** `DIARY_EGRESS=direct` takes Petersburg off the proxy too, so a partial rollback is a revert.
- **The failure a family sees.** A refused or down proxy reads as `UpstreamUnavailable`, which the bot words as the region's own outage. Only `diary_proxy` tells the owner which it is.
- **Which regions production has in use is unknown,** possibly none.
- **The tests cannot make a CONNECT.** The pools are told apart through httpx's private `_transport_for_url`, as `test_diary_proxy.py` already does.
- **The privacy text's claim about the proxy's log** («может записать их в свой журнал») is Squid's default. Check `access_log` in the RUVDS `squid.conf` before the merge.

    """Answer every region's probe with ``handler(proxy, request)``; returns each
    probe's proxy and request."""
    asked: list[tuple[str | None, httpx.Request]] = []

async def regions_in_use(session: AsyncSession) -> list[Region]:
    """The «Сетевой город» regions this deployment calls, by key: each a class is
    bound to (`classes.diary_region`) and each a live session is on, that the
    allow-list still serves with a password - sixteen at most. A region nobody

    bound = set(

            select(SchoolClass.diary_region).where(SchoolClass.diary_provider == NETSCHOOL)

async def check_diary_region(
    region: Region, settings: Settings, *, timeout: float = CHECK_TIMEOUT_SECONDS
) -> Result:
    """One ``GET /webapi/logindata`` of a region's server, by its calls' route.

    ``ok`` for any answer but a refusal: the route and the server both
    answered. ``failing`` for no answer, and for a 403 or a WAF's page - the
    client's own reading (`netschool.client.looks_refused`) - because a region
    refusing this address is a route that does not work, whatever it would say
    to anyone else. Sent with the diary client's own headers and user agent, so
    the region sees what a family's call looks like. The reason names the
    route, and never the proxy's address; the hint says what the owner can do.
    """
    from app.providers.diary.http import USER_AGENT
    from app.providers.netschool.client import HEADERS, PROBE, looks_refused

    proxy = proxy_for(NETSCHOOL, region.key, settings)
    way = "through the proxy" if proxy else "directly"
    hint = HINT_PROXIED if proxy else HINT_DIRECT
    loop = asyncio.get_running_loop()
    started = loop.time()
    try:
        async with _route_client(proxy, timeout) as client:
            response = await asyncio.wait_for(
                client.get(f"{region.origin}{PROBE}", headers={"user-agent": USER_AGENT, **HEADERS}),
                timeout,
            )
    except (httpx.TimeoutException, TimeoutError) as failure:
        return Result(
            FAILING, f"no answer {way}: {type(failure).__name__}", timed_out=True, hint=hint
        )
    except httpx.HTTPError as failure:
        return Result(FAILING, f"no answer {way}: {type(failure).__name__}", hint=hint)
    round_trip = round((loop.time() - started) * 1000)
    if looks_refused(response):
        return Result(
            FAILING,
            f"refused {way}: HTTP {response.status_code}",
            round_trip_ms=round_trip,
            hint=hint,
        )
    return Result(OK, f"HTTP {response.status_code} {way}", round_trip_ms=round_trip)

    return lambda timeout: check_diary_region(region, settings, timeout=timeout)
