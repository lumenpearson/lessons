# Хостинг

## Коротко

Есть два честных варианта, и выбор между ними — не про технологию, а про то,
согласны ли вы платить €4 в месяц.

| | Бесплатно: Vercel + Neon | ~€4/мес: маленький VPS |
| --- | --- | --- |
| Изменения в коде | webhook вместо polling, Postgres, FSM в БД | никаких |
| Отклик бота | 1–3 с на холодном старте | мгновенный |
| Надёжность | зависит от двух чужих бесплатных тарифов | зависит от вас |
| Сложность | заметная | `docker compose up` |

Если бесплатность — жёсткое требование, берите первый. Если четыре евро в
месяц приемлемы, второй проще, быстрее и не требует ничего переписывать.

## Почему Vercel не работает «как есть»

Три препятствия, и все настоящие.

**Бот использует long polling.** Он держит открытое соединение с Telegram и
ждёт. На Vercel нет долгоживущих процессов: функция просыпается на запрос и
умирает. Polling там невозможен в принципе. Нужен webhook — Telegram сам
стучится в ваш URL на каждое сообщение.

**SQLite не переживает деплой.** Файловая система функции эфемерная. База
должна быть внешней; Neon даёт бесплатный Postgres, а приложение уже умеет с
ним работать через `DATABASE_URL` с `asyncpg`.

**Состояние диалогов терялось бы между сообщениями.** aiogram по умолчанию
хранит незавершённые диалоги в памяти процесса. На serverless каждое сообщение
может попасть в новый экземпляр, поэтому бот забывал бы выбранную дату до того,
как вы введёте текст задания. Ломались бы все многошаговые сценарии: домашка,
приглашения, замены, события, расписание.

Все три решены. Webhook — `app/api/telegram.py`, монтируется только когда задан
секрет. Postgres приложение уже умеет. Состояние диалогов — `app/fsm_storage.py`,
в той же базе, что и данные; побочная польза в том, что редеплой больше не
обрывает начатые диалоги. 19 тестов на оба механизма.

## Вариант 1: Vercel + Neon

### Что нужно

1. Аккаунт [Neon](https://neon.tech) — бесплатный Postgres.
2. Аккаунт [Vercel](https://vercel.com), Hobby-тариф.
3. Токен бота от [@BotFather](https://t.me/BotFather).
4. Ваш Telegram id от [@userinfobot](https://t.me/userinfobot).

### Секреты

**Никогда не отправляйте токен в переписку, в коммит или в issue.** Токен даёт
полный контроль над ботом: читать все сообщения, отвечать от его имени, менять
его. Утёкший токен отзывается в @BotFather командой `/revoke`.

Правильное место — переменные окружения хостинга. В Vercel:
**Settings → Environment Variables**, и обязательно отметьте `Sensitive`, иначе
значение можно будет прочитать в интерфейсе.

| Переменная | Значение |
| --- | --- |
| `BOT_TOKEN` | токен от BotFather |
| `OWNER_IDS` | ваш Telegram id; несколько — через запятую, см. «Несколько владельцев» ниже |
| `DATABASE_URL` | строка подключения Neon, схема `postgresql+asyncpg://` |
| `TIMEZONE` | часовой пояс по умолчанию для новых классов |
| `WEBHOOK_SECRET` | случайная строка, см. ниже |
| `RUN_BOT` | `false` — polling на serverless не запускается |
| `CRON_SECRET` | случайная строка, см. «Напоминания» ниже |
| `BOT_USERNAME` | @имя бота без «@» — для ссылки привязки телефона |
| `PUBLIC_BASE_URL` | `https://ваш-проект.vercel.app` — для календаря и страницы входа в дневник |
| `DIARY_SECRET` | случайная строка, см. «Электронный дневник» ниже |

Переменные нужны и для Production, и для Preview, если хотите тестовый стенд.

`WEBHOOK_SECRET` придумайте сами и никому не показывайте:

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(32))"
```

`CRON_SECRET` придумайте так же. Без него эндпоинт напоминаний отвечает 404:
тик, который может запустить кто угодно, — это способ заставить бота написать
всем подписчикам когда вздумается.

### Несколько владельцев

`OWNER_IDS` принимает список — в одну строку, через запятую:

```
OWNER_IDS=111111111,222222222,333333333
```

Пробелы вокруг чисел срезаются, точка с запятой понимается наравне с запятой,
хвостовая запятая не мешает. Свой id скажет @userinfobot.

**Разделителем считается только запятая (или точка с запятой).** Поле значения
в интерфейсе Vercel многострочное и само провоцирует вписать по одному id на
строку — так список не прочитается вообще:

| Вписали | Прочиталось |
| --- | --- |
| `111,222,333` | `111, 222, 333` |
| `111, 222, 333` | `111, 222, 333` |
| `111;222;333` | `111, 222, 333` |
| `111,222,` | `111, 222` |
| `111 222 333` | **ничего** |
| по одному на строку | **ничего** |
| `111,222x,333` | **`111, 333`** |

Последние три строки — то, на чём тут обжигаются. Ошибка не объявляется никак:
бот запускается, ничего не пишет в лог, просто ни у кого (или у одного
конкретного человека) нет прав владельца. Разбор — `app/config.py`,
`Settings.owner_id_list`: всё, что не похоже на число, молча выбрасывается.

**Переменная читается при сборке.** Правка не распространяется на уже
работающий деплой — после изменения списка нужен Redeploy, иначе владельцы
останутся прежними.

Роль из `OWNER_IDS` перекрывает роль в классе: такой человек — владелец **во
всех** классах этого развёртывания, а не в одном. Выдать OWNER изнутри бота
нельзя и дорасти до него нельзя (`app/bot/roles.py`), поэтому и снять владельца
можно только правкой переменной с последующим передеплоем.

### Электронный дневник

`DIARY_SECRET` — ключ, которым шифруется сессия электронного дневника
(`app/crypto.py`). Это единственные учётные данные в проекте, которые нельзя
хранить хешем: токен дневника отправляется наверх при каждом запросе, поэтому он
шифруется, а не хешируется.

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(48))"
```

Без него дневник **выключается целиком**, а не работает с открытым текстом:
молчаливый откат к plaintext был бы невидим — фича отвечает, разница только в
колонке, куда никто не смотрит, — и развёртывания живут так годами.

Три вещи, которые стоит знать про этот ключ:

* **Он нужен только в окружении Vercel.** Секретом репозитория в GitHub Actions
  он не является: ни один workflow не импортирует этот код. Тесты задают свой
  ключ сами (`tests/conftest.py`), а `reminders.yml` только дёргает уже
  развёрнутый тик по HTTP.
* **Он должен совпадать во всех окружениях Vercel, которые ходят в одну базу.**
  Сессия, запечатанная в Preview, не откроется в Production под другим ключом.
  Ничего не ломается — нечитаемая сессия считается истёкшей и человек входит
  заново, — но выглядит это как баг.
* **Смена ключа разлогинивает всех.** Это законный способ отозвать разом все
  сохранённые сессии дневника, если есть подозрение на утечку базы.

Ещё дневнику нужен `PUBLIC_BASE_URL`: без него боту неоткуда взять адрес
страницы входа, и он честно об этом говорит вместо ссылки, которая вернёт 404.

`BOT_USERNAME` и `PUBLIC_BASE_URL` — не секреты, но и не угадываются. Первое
нужно, чтобы приложение показало ссылку `t.me/<бот>?start=link_<код>`; без него
код привязки всё равно работает, его просто набирают руками. Второе — адрес, по
которому бот отдаёт ссылку на календарь класса; сервер не берёт его из запроса,
потому что за Vercel функция видит внутренний хост, а бот строит ссылку вообще
без запроса.

Telegram присылает его в заголовке `X-Telegram-Bot-Api-Secret-Token` на каждом
запросе. Без проверки этого заголовка ваш webhook-адрес — открытый эндпоинт, в
который кто угодно может слать поддельные апдейты: назначить себя редактором,
переписать расписание, стереть домашку. Проверка обязательна.

### Строка подключения Neon

**Вставляйте как есть.** Приложение само приводит её к виду, который понимает
asyncpg: добавляет драйвер, переводит `sslmode` в параметр подключения, убирает
`channel_binding` и прочее, что понимает только libpq.

Neon предлагает две строки. **Берите ту, что с `-pooler` в адресе.** На
serverless экземпляры приходят и уходят, и каждый открывает свои соединения;
без пулера лимит Postgres кончится раньше, чем вы это заметите.

За это приходится платить одной неочевидностью, и она обрабатывается в коде.
PgBouncer в transaction-режиме отдаёт каждой транзакции любой свободный backend,
а asyncpg готовит запросы на том соединении, которое увидел первым. Рассинхрон
всплывает не на старте, а под нагрузкой, ошибкой вида
`prepared statement "__asyncpg_..." already exists`. Поэтому для пулера
кеширование подготовленных запросов выключается автоматически.

Прямая строка (без `-pooler`) тоже работает и даже чуть быстрее на один запрос —
но только если экземпляр один. Для Vercel это не тот случай.

### Создание и обновление схемы

Схемой управляет Alembic. Одна и та же команда годится и для пустой базы, и для
той, что уже работает:

```bash
cd server
DATABASE_URL='postgresql+asyncpg://...' .venv/bin/alembic upgrade head
```

Ревизия `0001` — это `create_all` с `checkfirst`, то есть на пустой базе она
создаёт всё, а на уже живой — только то, чего в ней нет, и берёт её под
управление Alembic, ничего не переписывая. Ревизия `0002` расширяет до 64 бит
пять колонок с Telegram-id: `Integer` на Postgres — это int4, а id в Telegram
перевалили за 2³¹ ещё в 2021 году, и первый же человек с современным id ронял
бота переполнением. Колонки, которые уже широкие, она не трогает. Дальше две
добавляющие: `0003` — личные задачи, отметки о сделанной домашке, напоминания,
запросы доступа, журнал, привязка устройств и токен календаря; `0004` — сессии
электронного дневника Петербурга, без колонки под пароль, потому что пароль не
хранится. `0005` добавляет колонку «на какой перемене столовая», `0006` шифрует
учётные данные дневника (и **удаляет** существующие сессии — запечатать их
значило бы сохранить ключи, которые уже лежали в бэкапах открытыми) и добавляет
колонки персонального дневника; `0007` добавляет два внешних ключа на
`classes.id`, которые `0006` объявить забыла. Все проверяют инспектором, чего в
базе уже нет, и не переписывают существующие таблицы, так что их можно
применять к живому классу посреди учебного дня. Голова сейчас — `0007`.

### Миграция идёт ПЕРЕД деплоем, а не после

Это не стилистика. Мердж в `main` деплоит на Vercel автоматически, миграция
запускается руками — и между ними есть окно, в котором код знает про колонку,
которой в базе нет. Так уже ронялся продакшен: код с `classes.diary_provider`
уехал раньше своей ревизии, ничего не упало при старте, а упал первый же
ORM-запрос к классу — то есть middleware бота, то есть **каждый** апдейт, с
`UndefinedColumnError` на сороковой строке трейсбека.

Правильный порядок:

1. `alembic upgrade head` на боевой базе;
2. только потом мердж (он же деплой).

Так можно именно потому, что все ревизии после `0001` — добавляющие: колонку,
про которую работающий код ещё не знает, он просто не читает. Обратный порядок
безопасным не бывает никогда.

Что база действительно догнала код, показывает `alembic current` — он должен
напечатать ту же ревизию, что `alembic heads`. То же самое, но по HTTP и не
заходя в базу руками:

```bash
curl -s https://<ваш-проект>.vercel.app/api/v1/warmup
```

`{"status":"ok","schema":"0007"}` — всё сошлось. `"status":"degraded"` вместе с
`expected_schema` означает, что база отстала, и называет обе ревизии.
`/api/v1/health` этого не покажет намеренно: он не открывает соединение с базой
вообще, иначе пинг ради прогрева будил бы уснувший Neon.

Запускается локально, с рабочей строкой подключения, а не из функции: миграция
берёт `ACCESS EXCLUSIVE` на таблицу, и делать это на холодном старте запроса —
плохая идея. Посмотреть SQL перед тем, как выполнять:

```bash
DATABASE_URL='postgresql+asyncpg://...' .venv/bin/alembic upgrade head --sql
```

Текущее состояние базы: `alembic current`. История: `alembic history`.

Отдельная команда, а не автоматика при старте: таблицы обычно создаёт lifespan
FastAPI, но serverless-платформа может вообще не вызывать lifespan. Понадеяться
на него — получить первый запрос с ошибкой «no such table» и без внятной
причины.

### Регистрация webhook

Один раз после деплоя:

```bash
curl -X POST "https://api.telegram.org/bot<ТОКЕН>/setWebhook" \
  -d "url=https://<ваш-проект>.vercel.app/api/v1/telegram/webhook" \
  -d "secret_token=<WEBHOOK_SECRET>" \
  -d "drop_pending_updates=true"
```

Проверить: `https://api.telegram.org/bot<ТОКЕН>/getWebhookInfo`. Поле
`last_error_message` покажет, почему Telegram не может достучаться.

Эту команду выполняете вы, у себя, — токен в ней открытым текстом.

### Почему секрет обязателен

Без него `webhook_enabled` возвращает `false` и эндпоинт вообще не монтируется.
Это не перестраховка. Telegram ничего не подписывает: он просто шлёт JSON, а бот
доверяет `user_id` внутри этого JSON, решая, кто может править расписание. Без
проверки секрета любой, кто угадает URL, отправляет поддельный апдейт с чужим
id — и это не спам, а полный захват бота.

Сравнение идёт через `hmac.compare_digest`, чтобы по времени ответа нельзя было
подобрать секрет посимвольно.

Ещё одна деталь: эндпоинт отвечает `200` даже если обработчик упал, а ошибка
уходит в лог. Telegram повторяет неуспешные доставки с нарастающей задержкой и
в конце концов отключает webhook — одно плохое сообщение не должно уносить бота
целиком.

### Чего ожидать

Первое сообщение боту после простоя обрабатывается 1–3 секунды: холодный старт
Python-функции плюс подключение к Neon. Дальше быстро, пока экземпляр живой.
Для дневника терпимо, но это не мгновенный отклик обычного бота.

Это две независимые задержки, а не одна, и они складываются:

1. **Холодный старт функции.** Vercel не держит экземпляр, если на него давно
   не было запросов: следующий запрос сначала поднимает интерпретатор Python и
   импортирует FastAPI, aiogram, SQLAlchemy — и только потом доходит до кода.
2. **Neon засыпает отдельно от функции.** На бесплатном тарифе вычислительный
   узел Neon приостанавливается сам, по своему таймауту простоя, независимо от
   того, жива ли функция Vercel. Первый запрос после этого ждёт, пока Neon
   проснётся, — и это происходит даже если функция уже тёплая.

Оба уже насколько возможно сокращены в коде: функция закреплена в `fra1`, рядом
с базой (см. «Почему Vercel не работает "как есть"» выше), а `create_all` при
старте выполняется только для локального SQLite, не для Postgres.

### Если и это медленно

Обе задержки — сама архитектура бесплатного пути, а не баг: serverless
специально не держит ничего постоянно запущенным, это то, за что не платят.
Убрать совсем можно двумя способами.

**Не спать самому.** Внешний планировщик, дёргающий эндпоинт раз в несколько
минут, держит и функцию, и Neon проснувшимися. Собственный Cron у Vercel на
Hobby-тарифе для этого не годится — минимальный интервал там суточный, то есть
между срабатываниями Neon успевает уснуть много раз. Нужен внешний сервис
(cron-job.org, UptimeRobot, healthchecks.io — у всех есть бесплатный тариф с
интервалом от одной минуты) или собственный scheduled workflow в этом же
GitHub-репозитории.

Важно, куда стучаться. `/api/v1/health` не трогает базу вовсе — держит тёплой
только функцию, а Neon всё равно засыпает по своему таймеру. Для двух
эндпоинтов сразу есть `/api/v1/warmup`: тот же ответ, но с одним `SELECT 1` по
дороге, — на него и настраивайте пинг, раз в 4–5 минут.

```bash
curl https://<ваш-проект>.vercel.app/api/v1/warmup
```

Это лишние вызовы функции — раз в несколько минут круглые сутки, стоит
сверить с лимитом бесплатного тарифа Vercel на число вызовов, если он есть на
момент чтения.

**Не спать не пытаться.** `~€4/мес VPS` (вариант 2 ниже) не засыпает вообще,
потому что процесс не serverless — ничего не переписывать, тот же код, просто
другой хостинг. Если холодный старт мешает больше, чем стоит бесплатность,
это более простое решение, чем поддерживать внешний пинг вечно.

## Вариант 2: свой сервер

Ничего переписывать не нужно — код уже так работает.

```bash
git clone https://github.com/lumenpearson/lessons && cd lessons
cp server/.env.example server/.env    # впишите BOT_TOKEN и OWNER_IDS
docker compose up -d --build
```

`docker-compose.yml` поднимает Postgres и приложение. Бот работает через
polling, поэтому внешний адрес и webhook не нужны вообще — сервер может стоять
за NAT без белого IP.

Приложению на телефоне нужен доступ к API. Варианты: белый IP с пробросом
порта, туннель вроде Cloudflare Tunnel, или, если все ученики в одной школьной
сети, просто локальный адрес.

Подойдёт любой VPS с 1 ГБ памяти. Нагрузка одного класса — это несколько сотен
запросов в день.

## Файлы для Vercel

| --- | --- |
| `api/index.py` | точка входа; тонкий реэкспорт `app.main:app`, чтобы serverless и `uvicorn` крутили один и тот же код |
| `vercel.json` | runtime, `maxDuration`, и rewrite всех путей на функцию |
| `requirements.txt` | Vercel не читает `pyproject.toml` из подкаталога; здесь только `asyncpg`, без `aiosqlite` |
| `.vercelignore` | не тащить в бандл `android/`, тесты и документацию |

## Что выбрать

Для одного класса и одного человека, который это поддерживает, **VPS проще**:
меньше движущихся частей, нет холодных стартов, не зависит от чужих бесплатных
тарифов, которые меняются.

**Vercel + Neon** оправдан, если платить нельзя или если классов станет много и
захочется не думать про сервер вообще.

## Напоминания: у сервера нет своих часов

На serverless между запросами не выполняется ничего, поэтому утренние и вечерние
сводки отправляет тот, кто позовёт `/api/v1/cron/tick` с заголовком
`X-Cron-Secret`. В репозитории это делает workflow `.github/workflows/reminders.yml`
каждые пять минут; ему нужны два секрета репозитория (**Settings → Secrets and
variables → Actions**):

| Секрет | Значение |
| --- | --- |
| `SERVER_URL` | `https://ваш-проект.vercel.app` |
| `CRON_SECRET` | то же значение, что в переменных окружения сервера |

Без этих секретов workflow не падает, а пишет notice и выходит с нулём — иначе
вкладка Actions краснела бы каждые пять минут у всякого, кто склонировал
репозиторий.

GitHub запускает расписания как получится: тик может опоздать на десять минут
или пропуститься. Это учтено: сервер решает, что отправить, по «что ещё не
отправлено сегодня», а не по «сработал ли прошлый тик», и отмечает отправку
до самой отправки — так падение посередине не рассылает сводку дважды.

Свой планировщик (cron-job.org, Uptime Robot, systemd timer — что угодно, что
умеет GET с заголовком) работает так же:

```bash
curl -fsS -H "X-Cron-Secret: $CRON_SECRET" \
  "https://ваш-проект.vercel.app/api/v1/cron/tick"
```

Тот же тик заодно подчищает брошенные диалоги бота и просроченные записи о
неудачных попытках ввода кода — на serverless это единственный момент, когда
вообще что-то можно подчистить.
